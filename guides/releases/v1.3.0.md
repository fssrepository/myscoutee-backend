# MyScoutee 1.3.0 — release preparation

Status: **unreleased**. This is a feature release. Historical releases and Git
tags, including 1.0.2, retain their original contents.

## Version identity

- Git release tag: `v1.3.0` on each participating repository's final release commit.
- Application, Java client, private admin client, Registry and MCP/plugin version:
  `1.3.0`. Frontend package and build metadata use the same version.
- Owned Docker images: `1.3.0-dev`, `1.3.0-e2e`, `1.3.0-prod` as applicable;
  nginx base: `1.3.0-base`. Standalone MCP/plugin Docker command: `1.3.0`.
- Debian version: `1.3.0`; release filenames and signed manifests use `1.3.0`.
  Upstream Mongo, Redis, MinIO and language/runtime versions are unchanged.

Use the existing release builders. Record the frontend submodule commit and the
sibling MCP, Registry and client commits before tagging the backend release.
Create an annotated `v1.3.0` tag at each final commit (`git tag -a v1.3.0 -m
"MyScoutee 1.3.0"`); never move or overwrite an older tag. Do not tag an
unfinished HEAD. Plugin builds remain unpublished; pushing an admin-client tag
runs its existing publishing workflow.

## MCP deployment and update boundary

The source dev/prod/E2E stacks and the packaged production Compose include the
MCP service. The existing nginx publishes anonymous `/mcp`, personal `/mcp/private` and the
OAuth metadata/token routes; private upstream networking,
read-only filesystem and an unprivileged user remain in force. Packaging binds
seven managed images, including MCP, to the release manifest. The update worker
checks the version-specific image set: six for pre-1.3.0 rollback targets, seven
from 1.3.0 onward. Missing MCP in a new candidate is rejected.

**1.0.2 → 1.3.0 uses the existing signed client installer, not the in-app updater.** The old installed
1.0.2 worker expects six images and cannot accept the new seven-image candidate.
The update-catalog signer rejects a pre-1.3.0 minimum version for seven-image
releases. The existing signed `packaging/client-tools/install.sh` verifies the
DEB before upload/installation and calls the package qualification command.
This path and subsequent rollback need artifact qualification on the designated
host. Source tests alone do not prove a real upgrade.
The 1.0.2 partial-container data helper is historical and unchanged.

## Remaining release gates

- Build/sign the final seven-image DEB and qualify install, upgrade, interruption
  and rollback from the declared supported source version.
- Run the existing NOT RUN API/group/help/mobile regression micros and record
  actual outcomes. Plugin/client live validation is separate from ZIP generation.
- Commit the verified sources, pin the frontend submodule, then create release
  tags. No Git tag, GitHub release or plugin publication has been made by this
  preparation.
