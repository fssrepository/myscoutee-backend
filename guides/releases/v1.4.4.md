# MyScoutee 1.4.4 — landing diagnostics, setup and startup performance

[MSC-125](https://github.com/fssrepository/myscoutee-roadmap/issues/163) adds a small, switchable probe to explain landing abandonment and browser-only entry failures through nginx.

The final 1.4.4 identities below include bounded diagnostic error details, global control of automatic consent prompts, setup-popup corrections, continuous guide background and the notification identity fix found through the probe. The existing 1.4.4 tags, releases and image aliases are overwritten at the user's request; MSC-125 source commits are consolidated per repository.

## Changes

- Nginx enables the probe through the existing HTML SSI path and a single default-off variable. It starts before Angular, so startup errors and very early departures can be reported.
- A bounded memory buffer sends at **15, 30, 45 and 60 seconds**, then releases its listeners/timers. Hidden/departing pages flush early; a native dialog can return within the same observation window. At most eight attempts, including early visibility flushes, are allowed. There is no browser storage, durable queue, retry loop or permanent heartbeat.
- Record the first trusted interaction and counts, missing local clicks/popups, setup/location permission states, notification decisions, external-browser handoff attempts, Firebase provider/popup outcomes, bootstrap/render/route milestones and bounded client-error fingerprints/code locations, cleaned messages (160 characters), up to three normalized stack frames and the reporting source (Angular, window, Promise or resource). Existing demo-list/article-list/API evidence remains in the ordinary access log.
- Empty-body diagnostic POSTs terminate at nginx with 204 and are written to **`/var/log/nginx/landing-debug.log`**, separately from the access log. Nothing is forwarded to the API, Redis or Mongo. Diagnostics redact URLs, emails, credential fields, quoted values, long identifiers, IPv4 addresses and precise decimal values; stack frames retain function names, JS basenames and positions. Raw messages/stacks are not copied verbatim. The existing 3500-character encoded-query limit is retained. Arbitrary third-party messages still require private handling.
- Add bounded lifecycle diagnostics for early hidden pages: original HTML prefetch/prerender and user-navigation header hints; initial/current visibility, focus, readiness, user activation and prerender state; DOM/load, freeze/resume, pageshow/pagehide and persisted flags; navigation/paint timings and continuous hidden duration. At most 12 lifecycle samples per batch, no extra timer/observer/storage, and the original 60-second/eight-attempt/3500-character bounds remain. A distinct pagehide or freeze can flush early. These are observations, not automatic conclusions about preloading, accidental taps or user intent.
- Extend the existing traffic analyzer to read both nginx logs and render the client reports alongside observed requests. Offline cached HTML cannot reactivate a previously enabled probe. The KVM gateway retains the same switch/sink with its writable temporary-log path.

- Correct notification cleanup identity: a cached token owner or a stale UI profile does not establish an HTTP login session. Signed-out landing preferences no longer issue a device DELETE as the previous member. An authenticated owner's server-side removal remains intact; retained OFF registrations are removed through the existing background flow when that owner signs in again. Failed background deletion retains its retry state, concurrent explicit/background removal shares one request, and a late token after logout cannot register the old user. Browser Push subscriptions and native permissions are untouched.
- Repair stale notification test setup and expectations: preparing a draft must not start the automatic write introduced in 1.4.3; DOM checks now exercise the actual saving controls instead of the removed Update button.

- Nginx controls automatic consent prompts globally with `X-MyScoutee-Consent-Auto` and the existing SSI document path. The image and Netcup default to `0`: manual privacy links still open the existing consent dialog, and actual acceptance/revocation state is retained.
- The permissions popup gains the existing consent flow as a fourth contextual action, with an outside red badge for missing acceptance. Connected static exclamation/check/block icons show each step. Temporary permission lookup, native decisions and saving do not become blocked states. The installation block remains visible, including in Instagram, with its button disabled when native installation is unavailable. Existing native installation and permission handlers are retained. Rows align left with a larger gap beside the status circles; no new animation is added.
- Opening consent preserves the parent permissions popup. The accepted-consent action reads **Revoke** instead of **Cancel**, using the existing translated label and existing removal action. Required-location text and the external-browser block retain their original content.

- Keep the guide background continuous from content loading through lazy rendering and initial positioning, using the existing visibility acknowledgement. The loading ring stops when the data arrives; no timer or animation is added. The first visible guide card retains its final position.

- Always show the existing browser-opening text and clickable action on every platform, including unknown browsers, without a visibility allowlist. Android retains its URL-handler intent. iPhone/iPad HTTPS links request Safari through `x-safari-https`; other and unidentified platforms attempt standard separate-window navigation. The embedding app may refuse the handoff; no automatic retry, timer or successful-handoff assumption is added. Current URL, query and fragment are retained, with unsafe protocols/credential URLs rejected. The 41 focused PWA/setup-popup tests passed; real iOS application-to-Safari handoff is not device-qualified.

## Startup performance follow-up

- Move the bounded landing probe into its external asset while retaining early execution and its existing memory-only limits.
- Load the existing entry popups through signals and the existing component launcher, without changing their existing actions. Consolidate static startup dependencies: the anonymous landing uses four JavaScript resources rather than the previous 102-resource graph. Home and navigation add three shared feature bundles rather than 29 small files; optional features remain lazy.
- Remove blanket service-worker prefetching of all feature JavaScript and font variants. Cache startup resources at installation and optional resources when used. Share the initial translation/version requests and keep font declarations in the external stylesheet to avoid duplicate downloads. HTTP/2 remains enabled.
- Read only the active help-document revision for the requested type/language instead of mapping the complete help history. Local matched API measurements fell from approximately 590 ms to 10 ms, with identical responses in 12 language/type cases.
- Batch the demo selector's existing country checks and project only the required profile fields. In ten warmed serial local requests, member-list median latency fell from 270 ms to 124 ms; application-container CPU time fell from 1111 ms to 281 ms. Eight role/limit response variants remained identical. Frontend local demo behavior and its existing delays are unchanged.
- The follow-up passed 72 focused backend/transport tests and 34 startup/service-worker tests. Local measurements do not establish production mobile latency. KVM runtime replay was unavailable because libvirt was inactive.
- Use the already saved location approval when deciding entry readiness. Opening the permissions panel still refreshes its native state; an inactive panel no longer refreshes on browser focus. Profile loading consumes any previously staged coordinates without acquiring another position. The existing manual location update and periodic tracking flow are retained.
- Give a lazily created login popup its current open/mobile inputs immediately. Three reload-and-single-click checks on the physical Android phone opened the login panel on the first click, without an automatic setup popup or fresh native location lookup.
- After the server accepts an HTTP demo login, hand off to the existing avatar load ring while the protected page and profile finish loading. Close the retained selector before removing that loading view; rejected navigation restores the same selector for retry. Frontend-local entry and its existing delays are unchanged.
- On the physical Android phone against VMware, the visible handoff moved from 1021 ms to 221/248 ms in two final reload runs, with no selector reappearance or JavaScript error. Full readiness was 1662 ms before and 1770/1699 ms after; the longest recorded JavaScript task was 256 ms before and 268/283 ms after. This improves the loading feedback, not the total computation time. The latest 86 focused tests passed; the preceding permission/profile batch passed 212 tests and the first-click popup regression passed 4 tests. Counts overlap and are not summed.

## Operation and limits

Automatic consent prompting is controlled separately by `map $host $myscoutee_consent_auto { default 0; }` in nginx. Change it to `1`, validate and reload to restore automatic prompts. The response header reflects that server-selected value; a client request header cannot override it. Manual consent remains available in either mode.

The image defaults to measurement off. On Netcup, the temporary probe is enabled after deployment. To disable it, change `map $host $myscoutee_landing_debug { default 1; }` back to `default 0;` in `/etc/nginx/nginx.conf`, then validate and reload nginx. An in-container activation is also cleared when nginx is recreated. See [the traffic tool](../../tools/traffic/README.md#temporary-landing-probe-msc-125-default-off) for details.

The dedicated debug file is container-local; preserve a private copy before replacement when needed. Beacon acceptance does not prove delivery. Closing before JavaScript starts can leave only the ordinary HTML request; missing reports do not establish disinterest. A native popup/handoff request does not prove the browser opened it, and a render callback does not prove the visitor saw it. Raw errors and visitor timelines are not published.
