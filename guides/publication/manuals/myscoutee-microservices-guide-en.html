1. Architecture and Ownership

Business source remains in server/projects/profile/src/main/java/com/raxim/myscoutee/domain. The legacy projects/profile name is intentional. The monolith and service builds compile the same source. The microservices/ shell owns composition, entry points, transport and deployment. It can later move into a separate repository mounted as a submodule.

Canonical domains own business behavior and configuration; the microservices shell owns assembly, transport and deployment. The monolith remains buildable without the shell. One shared CoreApplication source is compiled into each selected artifact.

1.1 Read the system in layers

A source domain, a service image, a container and a virtual machine are different things. A domain groups Java responsibilities. An assembly selects domains and produces one executable image. A running image becomes a container. Kubernetes places containers in pods inside the Ubuntu guest. KVM runs that guest on the developer's physical computer. Several independent application processes therefore share one guest, instead of requiring one VM per service.

The tools used here and the question each answers
Layer / toolResponsibility in this repository
Gradle + Docker image buildWhich canonical source and runtime dependencies go into each immutable application package?
KVM + QEMUHow does the headless Ubuntu guest execute with virtual CPU, memory, disks and a network interface? KVM supplies Linux hardware virtualization; QEMU supplies the machine and devices.
libvirt + virshWhich guest, storage pool and virtual network exist, and are they running? libvirt manages QEMU; virsh is its command-line client.
TerraformWhich of those infrastructure resources should exist, and which existing resource does each declaration own?
cloud-init + systemdHow is a fresh guest configured, and how does its k3s service start when that guest boots?
k3s / Kubernetes + containerdWhich pods should run inside the guest? Kubernetes reconciles workloads; containerd actually runs their containers.
HelmWhich versioned templates and values describe the application Deployments, Services, configuration, credentials and volume claims?
PrometheusWhat numerical measurements have the configured targets exposed over time?
GrafanaHow can an operator query and compare those measurements in dashboards?

Follow one change through these layers: changing a Java domain needs a new assembly image; changing which domains share a process changes assemblies.json; changing VM memory changes infrastructure. A Grafana panel changes presentation of measurements. Diagnose and edit the layer that owns the problem before restarting surrounding layers.

1.2 Current physical placement

The workload box contains all eight backends and eight supporting Deployments. Host Docker builds images and runs monitoring; the guest uses containerd, so host docker ps does not list guest pods. Monitoring lives beside the VM, outside Kubernetes. Its application scrape targets need an explicit private network connection; simply installing Kubernetes does not provide that connection.

2. Build and Artifact Boundaries

Commands below run from the backend repository root. Check the current host first. If a dev watcher already owns compilation, follow the repository runtime rule; never run a competing build.

microservices/tools/lab.sh preflight
microservices/tools/lab.sh jars
microservices/tools/lab.sh images

build combines the last two steps. The wrapper uses serial Gradle execution and the backend's existing wrapper, dependency catalog and security overrides. It does not reuse the monolith's compiled output.

OutputPurpose
build/<service>/libs/Independent executable JAR
build/<service>/generated/Precise component/repository configuration and production resources
build/deployment/Per-service Dockerfile and monitoring targets
build/reports/assemblies.jsonJAR hashes, sizes, dependency and package ownership evidence

The audit rejects foreign implementation packages, duplicate application classes, the monolith entry point and development resources. API/DTO contracts are compiled once into a shared library. Existing Java projections are not automatically safe wire schemas.

Images use the canonical production YAML and Java 25 JRE, separate dependency/application layers, user 10001, bounded heaps and fail-fast OOM handling. Only the assets runtime carries ImageMagick/WebP tools. No source mounts, sync containers, watchers, DevTools or build tools belong in the measured runtime.

To build from a future separate shell checkout, set MYSCOUTEE_BACKEND_SOURCE to the compatible backend source checkout. Preserve the canonical source path; copying domain code creates another owner and is unnecessary.

2.1 Image versions and reuse

# Explicit release actions, only after relevant source changes:
microservices/tools/lab.sh frontend-image
python3 microservices/tools/workloads.py lock-images

# Ordinary deployment: import missing versions; never build implicitly.
python3 microservices/tools/workloads.py up

deploy/images.lock.json records full Docker image configuration IDs, content fingerprints and version references. A reference such as myscoutee-service-assets:0.1.0-<hash> is checked against its full ID before reuse. The host and guest have different image stores. import-images streams only missing locked images from host Docker to guest containerd over the existing pinned SSH connection. Repeated deployment reuses the locked guest cache without rebuilding. The inventory now contains eight backend and nine supporting images.

Kubernetes uses IfNotPresent. This single-node lab does not need an additional registry container. Custom tags are local artifacts, not published Docker Hub images: a new machine must receive the matching artifact or build it explicitly. A future registry can distribute published versions; cache presence and exact identity must still be verified.

3. Communication and Execution Context

The first implemented boundary retains localization.api.TranslationBundles. The canonical I18nService owns bundle selection, language fallback, mode-specific caches and version semantics. The shell supplies a typed HTTP adapter and a thin endpoint.

GET /_internal/v1/localization/bundle
Authorization: Bearer <dedicated localization-read secret>
X-MyScoutee-Session-Mode: REAL | DEMO

The checked-in contract is microservices/transport/contracts/localization/localization-v1.openapi.json. Optional query parameters are lang, acceptLanguage and version. The response reuses I18nBundleResponseDto; a current version returns data: null, preserving the canonical distinction from an empty map.

The generated assembly imports the server configuration in the localization owner. An assembly importing TranslationBundles without owning localization receives the client configuration. With the current grouping, identity is a remote consumer; email remains local within communication.

Production requires a trusted TLS path and credential custody/rotation. A read credential for global translations is not proof of delegated account or workspace authority.

Limits are 32 URLs, a 1-MiB body including chunked transfers and a 4-KiB response for small projections. Event member projections and chat-reference lists allow up to 2 MiB. These service capabilities supply facts to media authorization; they do not authenticate a user or grant access to a file.

The existing localization transport supplies the shared timeout, concurrency, credential and mode-context implementation. The assembly audit also verifies actual client/server imports in the compiled configuration, including consumers that use fully qualified Java names.

3.2 Focused profile identity reads

accounts.api.ProfileIdentities returns ProfileIdentityDto containing only user ID, account ID and workspace ID. Separate operations preserve the canonical first-profile lookup, non-deleted existence check and workspace user-ID list. The canonical ProfileDirectoryService owns these queries; the shell transports them through profile-identities-v1.openapi.json. Payment administration, affiliate validation and refund notification reuse this port. Their existing authorization and notification rules remain in their canonical owners.

This is a use-case contract, not a serialized profile document. Other profile consumers still need reviewed contracts for the facts they use. A service read credential does not delegate the caller's administrative role or workspace authority.

The binding inventory associates each port with its owning domain, explicit Spring configurations, configuration prefix and private credential name. The build selects local owner or remote client; the workload renderer resolves the owner's Kubernetes Service name. Credential migration adds missing secrets atomically without replacing existing values.

3.3 Chat directory reads

chat-directory-v1.openapi.json transports the existing owner/chat lookup, all directory views for a chat, unread version and support counts. ChatDirectoryEntryDto carries only the existing directory interface fields, including member IDs and support status. Chat messages, persistence IDs and other document fields are excluded. Tests wrap the canonical directory service with repository/Mongo fixtures, preserving null versus empty values, REAL/DEMO scope and aggregate-count semantics.

3.5 Membership reads and policy facts

member-directory-v1.openapi.json transports the existing membership lookup/list, batch, page and VIP-pricing operations. The detached member DTO excludes attendance, counters and invitation audit. Queries are bounded to 4096 owner IDs and 1 MiB; pages accept 1–1000 entries and responses at most 2 MiB. Canonical VIP eligibility remains owner-side. Errors never turn into absent membership or free pricing.

EventMembershipFacts and AssetMembershipFacts narrow their existing ownership APIs to the fields read by MemberPolicyFacts. Their DTOs contain five event fields and four asset fields. Local services retain the original queries through API inheritance; the shell adds explicit HTTP transport. Workspace filtering, lifecycle and role policy remain unchanged. Existing canonical access-control/resource tests cover those rules; HTTP fixtures cover the detached projections and session-mode boundary.

GroupDirectory retains its nine existing directory operations, including owner-computed lifecycle and moderation facts. Its DTO implements the existing read view; group policy derivation is not repeated in the HTTP client. CommunityMembershipReads narrows CommunityMemberships to the two reads used by account workspace selection. Membership registration and transitions stay owner-local.

EdgeDirectory exposes the two existing affinity directory reads. AffinityEdgeDto contains exactly the seven interface fields; private matching evidence is excluded. The batch accepts at most 4096 identifiers and 1 MiB, and responses are bounded to 2 MiB. Owner failure is reported as an error, never an empty network.

RatingDirectory retains four canonical reads and the existing 23-field rating view. Supplemental actor snapshots are excluded. Home-game exclusion projections remain sparse, and positive campaign ratings use the original owner query; HTTP tests cover those semantics, decimal scores, null fields and owner failures.

ChatReview transports reported-message and report-evidence reads while retaining canonical membership/author checks and message order. EventHomeReads narrows the home activity/report queries to thirteen consumed event fields; FeedbackDirectory preserves the existing target-user query and answer view. The unused asset ownership dependency was removed from the home consumer.

Remaining communication work Actor/workspace validation, other domain adapters and public authentication remain open. The nginx routing table exists, but routing cannot supply absent application bindings. SDK handles, servlet objects and callback interfaces cannot be serialized into generic RPC. Payment finalization must reconcile an unknown remote outcome before compensation; a timeout alone does not justify a refund. Reuse the existing payment coordinator and integration outbox owners.

3.6 Discovery, gateway and failure recovery

A Kubernetes Service supplies a stable address; CoreDNS resolves its service name to that address. This is service discovery. The typed adapter still serializes a request, carries REAL/DEMO and workspace context, checks authority, imposes limits and validates the reply. OpenAPI describes this wire contract. DNS does not implement Java calls, and a service mesh would not make a multi-owner mutation atomic. No mesh is installed in this lab.

The frontend Nginx also routes public API paths to their owning assembly. This is the current gateway layer. Signed short-lived actor delegation carries the existing authenticated identity across internal calls; private capability credentials restrict which producer can invoke each owner. Keep business policies in their existing domains. An empty-body health response is neither an authorization decision nor a completed business operation.

Recovery belongs to the business owner that accepted the command. Contact access now records an immutable accounts-owned command before the chat write, retains its receipt, applies version-guarded account effects and uses the existing notification outbox with a stable operation key. Profile status propagation retains its pending marker with the profile save and uses the existing affinity queue. Integration image retries use deterministic keys for the same owner/entity/content; uncertain resource creation must not delete a possibly referenced image. A successful payment fulfillment followed by a failed receipt save remains pending for gateway redelivery, never an automatic refund.

The accumulated standard, embedded recovery and adapter checks pass for these additions. Notification queue counts are a write-side projection refreshed by its existing worker, so they converge after a crash and may briefly lag concurrent writes. Provider push delivery retains its existing at-least-once behavior; an external provider without an idempotent receipt cannot promise exactly-once delivery. This does not require deploying a new broker or a general saga engine.

4. Developer-Host Installation and VM Lifecycle

4.1 What the host owns and what the guest owns

Headless means there is no desktop installed in the guest. Its Linux services are inspected over authenticated SSH. The physical host keeps the virtualization packages; guest packages, Kubernetes data and eventual application volumes live on the VM disk. Destroying the VM removes that guest data, while host package removal is a separate tracked operation.

The inspected host is Ubuntu 22.04 on x86-64 with KVM support and approximately 16 GiB physical memory. The host installer intentionally supports this inspected platform. Capacity and route checks run again before startup; historical free memory is not a startup guarantee.

bash microservices/tools/setup-host.sh
python3 microservices/tools/vm.py preflight
python3 microservices/tools/vm.py start
python3 microservices/tools/vm.py status
python3 microservices/tools/vm.py observe

Run setup in your terminal. sudo handles password entry; no script stores or reads the password. Host setup records package versions, existing packages, service ownership and added group membership before changing them. It installs headless QEMU/libvirt dependencies and starts the host services for the current session only.

4.2 Desired state, recorded identity and first boot

Terraform configuration describes the desired resources. Its provider translates that configuration into libvirt operations. plan compares declarations, recorded identities and live resources; apply performs the proposed changes. Here vm.py start runs both with additional ownership and safety checks. Re-running an unchanged start should report No changes; it must not create a second VM.

The seven managed objects are the VM, NAT network, directory storage pool, base Ubuntu volume, writable system volume, cloud-init disk generation and its uploaded volume. The system disk stores changes over the verified base image. Its 40 GiB capacity is sparse: this is a growth limit, not 40 GiB allocated immediately.

The cloud-init ISO supplies the initial user, SSH public key, packages and k3s configuration to a fresh guest. Cloud-init is initial provisioning, not a continuous configuration reconciler. The guest installer can reconcile its pinned k3s files, but changing cloud-init input on an existing VM is not automatically a safe live upgrade. The startup wrapper rejects a plan that would replace persistent resources; review such changes explicitly.

Terraform is the declarative owner of the VM, storage pool, volumes and NAT network. Its private state records resource identities so later runs can reconcile the same resources and remove only those resources. Cloud-init installs the guest dependencies and versioned k3s service. Terraform does not itself uninstall host packages.

The default host reserve remains 2048 MiB. An explicit vm.py start --host-reserve-mib 1536 applies a smaller reserve to that invocation only, as authorized for this host. It does not shrink the 8192-MiB guest or persist a weaker default. The monolith E2E stack and KVM lab must run serially; stop the VM completely before bash microservices/tools/check-current-monolith.sh. That script builds the current backend, reuses the canonical disposable E2E stack and scenarios, records private evidence, and stops its stack on exit.

The VM, lab network, pool and newly installed host daemons must not autostart after a host reboot. Guest k3s may start when the VM is explicitly started. The checks include libvirt sockets and guest save/resume, not only the VM autostart flag. No VMware or desktop guest is involved.

Startup rejects conflicting subnets, lost resource identity, insufficient memory and a plan that would replace persistent disks. Failed provisioning retains state for diagnosis. Ubuntu AppArmor remains enforcing: explicit disk and backing-image paths belong in the domain definition.

Guest SSH identity is obtained through the authenticated libvirt guest-agent channel and stored in the private known-hosts file. Guest access does not alter normal SSH configuration. Kubeconfig is copied to private lab state, never to the user's default Kubernetes configuration.

A kubeconfig contains the API address and credentials used by Kubernetes clients. Treat it as private access material, just like the guest SSH key. Terraform state is also private operational state; it is not a disposable cache. Losing it breaks the safe association between declarations and existing resources.

The eight source-defined application memory caps total 6400 MiB; their Java heaps total 3200 MiB. These are per-container upper bounds, not committed RAM. The 8192 MiB guest also needs room for native JVM memory within each cap, guest OS, k3s, data services and frontend/routing. Available memory is checked before replica/load runs. Host monitoring adds up to 512 MiB outside the guest, plus virtualization overhead. These budgets need measurement under load; a successful VM preflight does not prove that the completed application fits.

4.4 A normal session

  1. Install once with setup-host.sh, entering sudo credentials in your terminal. Builds and VM startup must respect the existing dev-owner rule.
  2. After a host reboot, explicitly run sudo python3 microservices/tools/host.py start. This starts the installed host services for this session.
  3. Run vm.py start. Expect a longer first run for verified downloads and guest setup; later starts retain guest identity and disks.
  4. Wait for cloud-init completion and the k3s API readiness message. Then inspect the node and workloads as described next; API readiness alone is not application readiness.
  5. Start monitoring separately with lab.sh monitoring-up. End the session with vm.py stop and lab.sh monitoring-stop to retain data.

5. Kubernetes and Live Runtime Inspection

5.1 The Kubernetes objects used in this lab

k3s is the Kubernetes distribution installed inside the guest. One server node runs both the control plane, which stores desired state and coordinates work, and the worker components, which execute containers. The default embedded SQLite database stores Kubernetes state; it is separate from the application's MongoDB. This one-VM topology provides a realistic process/network boundary, but no protection against losing that VM or physical host.

TermMeaning here
NodeThe Ubuntu VM registered as myscoutee-msc121. Its Ready condition describes the worker's ability to accept work.
Pod / containerA pod is Kubernetes' scheduling unit. A container is the running image inside it. For the planned application, each assembly starts its own JVM container; pod identities may change when replaced.
DeploymentA desired set of replaceable pod replicas and their image/configuration. Each of the eight backend Deployments normally has one replica. The bounded scale experiment temporarily gives assets two replicas and restores one afterwards.
Service / CoreDNSA Service gives selected pods a stable cluster address. CoreDNS resolves service names inside the cluster. A Service does not automatically expose its pods at the host's localhost.
NamespaceA grouping of cluster objects. kube-system contains system components. This is not a MyScoutee tenant, workspace or REAL/DEMO database boundary.
Local-path storageThe bundled provisioner can create persistent storage on the guest disk. A volume can outlive a pod, but destroying this VM destroys its local backing data.

Traefik, ServiceLB and metrics-server are deliberately disabled in this configuration. There is currently no automatic application ingress or load balancer, and kubectl top is unavailable. Use containerd statistics through k3s crictl stats for the requested docker-stats-like view. No additional dashboard server is needed for that view.

The Helm chart mounts a native image volume read-only at /docker-entrypoint-initdb.d. Its data-only OCI artifact contains the existing init scripts and REAL/DEMO seed directories. The standard Mongo image initializes an empty data volume through its own entrypoint, as in Compose. The seed artifact uses the existing support-image build, immutable image lock and registry/cache delivery. It needs no host directory, separate import job or copying init container. REAL system catalogs and production DEMO content stay separate; E2E fixtures are excluded. Existing database volumes are preserved and are not automatically reimported.

Shared two-member Mongo replica set

deploy/runtime.json enables mongoReplicaSet. Both members reuse the locked Mongo image, with a 768-MiB memory limit and 256-MiB WiredTiger cache per member. The configured Mongo CPU ceiling is three cores; it shares the existing four guest CPUs with the other pods. Primary reads preserve consistency and do not distribute read load to the secondary automatically.

python3 microservices/tools/mongo_replica.py configure
python3 microservices/tools/mongo_replica.py status

The conversion script stops backend writers, creates and validates a private authenticated archive, retains the original PVC, deploys the second member, initializes only the expected replica set, compares collection counts, and verifies a majority write by reading the secondary before deleting the probe. It then restores the backends. The repeat run verifies the receipt and configuration without another conversion or shutdown. Keys, backups and credentials stay outside Git. Normal stop includes both members; destroying the owned VM also deletes its backups and volumes.

Each Mongo member has a headless Service (clusterIP: None) with publishNotReadyAddresses: true. CoreDNS therefore publishes its pod address before readiness. The existing init container waits until that member name resolves to its own pod IP before starting Mongo. This avoids a simultaneous-restart bootstrap cycle where Mongo cannot identify itself through an unready Service. The workload reconciler migrates only the two owned member Services while backend writers are stopped; volumes are retained.

Two voting members need both for majority writes. This demonstrates replication, not continued writes after a member or host fails. No arbiter or secondary-read policy is added. Never disable the replica-set flag as an implicit data rollback.

Mongo uses the existing production importer and its collection allowlist from server/.env. The canonical myscoutee_db and demo_db sources map to the isolated msc121_real and msc121_demo databases. Bootstrap requires empty databases and stopped backends. Its durable content fingerprint permits identical interrupted work to resume and makes repeated completed bootstrap a no-op. A changed seed or namespace is rejected; this command does not update an existing application's data.

The explicit seed-mongo.py recovery/migration commands apply to older installations with their bootstrap marker. Their --verify and --restart modes require stopped backends. New installations initialize through the mounted scripts and use the normal application/data checks; they do not require a separate manual seed command.

The canonical bootstrap separates REAL and DEMO identities and imports articles, translation messages and policy definitions through their existing seed owners. The MinIO audit compares source keys and SHA-256 hashes with packaged files and actual S3 objects. Application uploads are preserved.

The registry's native DEMO seed and rolling QMAU refresh run through start-demo. The payment simulator initializes its SQLite state and built-in DEMO cards with the same code used by prod. Lab keys and persistent state are isolated. The restart check verifies retained registry seed/signing identity and simulator configuration/credential. Kubernetes volume ownership uses OnRootMismatch; a non-root init container restores owner-only 0600 permissions on the existing registry signing key and VOPRF keyring. It neither reads nor regenerates those keys. Redis is cache, and MCP/STUN need no separate business-data import. The frontend remains the canonical packaged bundle. Backend cache loaders and index initializers stay in their owning domains.

6. Prometheus, Grafana and Localhost Access

6.1 Collection, storage and display

The measurement path is Spring/Micrometer → private HTTP metrics endpoint → Prometheus → Grafana → browser. Micrometer exposes measurements from each JVM. Prometheus periodically reads those endpoints, records time series and evaluates queries. Grafana's provisioned datasource points to Prometheus and its panels display query results. Grafana does not collect JVM measurements itself.

In this implementation, render-deployment.py generates Prometheus targets from assemblies.json. Scrapes run every 30 seconds with a five-second timeout. The Grafana dashboard also refreshes every 30 seconds. Its datasource uses http://127.0.0.1:19090. Both monitoring containers use host networking with explicit loopback-only listeners; this lets Prometheus reach the libvirt guest without Docker bridge forwarding or changes to host firewall rules.

7. Bounded Stress and Further Qualification

The bounded load harness uses microservices/tools/check-load.py against six actual authenticated application routes, plus the separate two-pod contact-write harness. These reuse the lab’s native session and deployment helpers. For broader business stress campaigns, use the existing tests/e2e/stress/backend runner and scenarios with the microservices localhost ingress; do not start its monolith Compose example alongside the lab.

The following sequence also applies when extending the measured flow set:

  1. Complete the remote bindings and authenticated execution context required by the selected full-application flows.
  2. Deploy production-style application images, one shared Mongo replica set, required Redis/object storage and bounded monitoring into the owned lab.
  3. Prepare isolated canonical fixtures once, exit the preparation process, then verify REAL/DEMO and workspace behavior through the public API.
  4. Open the localhost application for the user. Preserve the repository's manual-QA/browser-control boundary unless full-flow browser testing is explicitly delegated.
  5. Run a recorded contract/flow smoke test, then the applicable stress scenarios and bounded load ramp. Do not interpret failed business assertions as acceptable performance.
  6. Record exact image identities, fixture identity, concurrency, resource limits, error rate, throughput, p50/p95/p99 latency, CPU, memory and database behavior.
  7. Compare against an equivalent monolith baseline serially on this machine. Keep build time and fixture preparation outside timed results.

The read-load harness can temporarily add a second assets replica. It records request failures, route latency and resource samples, then revokes its session and restores the replica count. Keep reports with the associated QA evidence; a bounded read run does not establish write saturation or production exhaustion limits.

python3 microservices/tools/check-load.py --two-assets --seconds 60 --concurrency 8

Same-scenario monolith comparison

Compare deployments serially with the same source revisions, workload, data, concurrency, warmup and resource limits. Record increases as well as decreases in latency, throughput and resource use. A historical result with different host load, cache state or fixtures cannot isolate an architecture regression.

The existing server-events-read and server-read-sweep profiles reuse the same assertions behind either architecture. Native DEMO sessions and canonical lab data differ from an isolated monolith E2E seed; record that difference when comparing deployed systems. Functional success alone does not establish performance parity.

9. Rules for Future Changes

The trust kernel routes backend domain/dependency/configuration/worker/transport/deployment changes to .agents/trust/reviews/microservices-compatibility.md. New agents must preserve both deployment forms.

  • Keep cross-domain dependencies on API/DTO contracts, with one implementation owner. Avoid foreign services, repositories and documents.
  • Make domain Spring configuration usable in the monolith and selected assemblies; keep shell-only imports out of canonical code.
  • Review network cost when an interface moves across processes. Batch hot reads and avoid remote calls inside per-item loops.
  • Keep schedulers, indexes and durable side effects under explicit ownership. Replica count must not create duplicate work.
  • Propagate validated identity and scope, restore contexts on errors, and treat remote timeout as an unknown outcome for mutations.
  • Extend the actual owner of compensation, retry or outbox behavior. Introduce saga infrastructure only for a proven missing capability.
  • Keep every installation and cleanup step versioned and idempotent. Secrets, state and VM disks stay outside Git.

10.2 Coordinated writer upgrade

The assets, events and feedbackStates owners initialize missing document versions before accepting writes. All old backend writers must be stopped before running new contexts or deploying new images. The lab deployment guard refuses a changed backend image while an old backend pod remains. Supporting services and volumes stay available.

python3 microservices/tools/workloads.py backends-stop
python3 microservices/tools/check-contexts.py
# Build and lock images explicitly before deployment; up never builds.
python3 microservices/tools/workloads.py up

A monolith upgrade needs the same stop-old/start-new boundary. Rollback to a pre-version writer requires a matched database backup, not merely an old image. Integration image imports retain deterministic partial objects after an unknown result; automatic orphan garbage collection is not included. Provider delivery remains at least once. Publication's existing invitation, reminder, chat and tournament flows still require full-flow qualification; the lifecycle receipt alone does not prove those adjacent effects.

10.3 Background CPU and repeated owner calls

Inspect private request metrics together with per-thread and container CPU samples to distinguish incoming owner calls from local polling. Include startup, JIT and periodic jobs when interpreting short samples.

The shared scheduled-group orchestration calls the existing atomic scheduled claim, which checks enabled state, due time and ownership. Affinity layout likewise uses one owner call for the claim instead of separate find, due and claim calls. Preserve missing, disabled and not-due rejection, acknowledged-claim execution and exclusion of another run when changing these paths.

Batch owner reads and reuse atomic owner operations where their existing semantics fit. Fewer remote requests can reduce work, but a sustained CPU or latency improvement requires a matched measurement.
