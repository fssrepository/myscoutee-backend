1. Purpose, scope, and use

This manual makes actions performed in MyScoutee's privileged workspaces repeatable, verifiable, and traceable. It covers the application-level Admin and Operator workspaces and defines the handoff boundary to the host operator.

Included in this manual

  • moderation and support;
  • content, articles, and platform parameters;
  • scheduled jobs and observability views;
  • node, deployment, and network Operator actions;
  • minimum verification, audit, and escalation controls.

This manual does not replace

  • the Operations Manual or the backup and recovery plan;
  • the organization's privacy and moderation policies;
  • the payment provider's own procedures;
  • Firebase and domain-provider administration.

Usage conventions

Menu and button labels are shown in bold. In a procedure, “record” means the external change ticket, incident record, or other register designated by the organization. MyScoutee does not provide a dedicated administrator-comment field on every screen.

Evidence rule This manual treats a function as available only when it is present in the 1.4.1 source and interface. Where there is no self-service UI, revocation control, or complete audit view, the limitation is stated explicitly.

2. Roles and responsibility boundaries

2.1. Admin, Operator, and host operator

Admin A

Application-level moderator and content/configuration manager. Has access to the /admin workspace.

Typical work: reports, blocks, support chats, content, articles, parameters, jobs, and observability.

Operator O

Network and deployment administrator for an installed MyScoutee node. Has access to the /operator workspace.

Typical work: registry connection, claims, updates, TLS, Firebase, branding, payments, measurement delivery, and revenue delivery.

Host operator

Owner of the operating system, packages, containers, database, network, and backups. This is not a MyScoutee web role and does not grant A or O authority by itself.

Typical work: service recovery, backup and restore, key files, storage, system time, proxy, DNS, and privileged workers.

Event host

A normal application user who manages an event or resource. This is distinct from the host operator and does not grant Admin or Operator access.

Activity Admin Operator Host operator
Investigate a user report Performs the action No responsibility Technical support only
Change administrator email addresses Affected party / verifier Performs the action Emergency recovery
Registry connection or ownership claim No responsibility Performs the action Supports network troubleshooting
Application parameter or schedule Performs the action No direct interface Reviews capacity and incident impact
TLS, Firebase, or payment configuration Impact verifier Performs the action Supports DNS, proxy, and secret handling
Backup and restore Business verifier May initiate an update Performs the action
Authorities do not inherit from one another A and O are separate backend authorities. The Admin interface does not grant Operator actions, and the Operator interface does not grant moderation rights. A person can access both only when their identity has been explicitly and verifiably assigned both authorities; never assume this by default.

2.2. Four-eyes principle and prohibited practices

Independent verification is required for actions that affect access, legal content, user accounts, payment routing, authentication, or service availability.

  • The change ticket identifies the purpose, owner, window, and rollback plan.
  • A second person compares the target value with the approved source.
  • The executor does not place secrets in screenshots, chats, or tickets.
  • A separate person verifies user impact after execution.
Prohibited Shared administrator accounts, sharing personal tokens, placing production secrets in unapproved channels, blocking without evidence, activating unapproved legal content, and updating without recovery readiness are prohibited.

3. Access and session security

3.1. Admin sign-in

In production, Admin authority is tied to configured administrator email addresses. The user authenticates with Firebase, after which the application routes an authorized identity to /admin. The web interface does not maintain a separate MyScoutee administrator password.

Start an Admin session

  1. Open only the approved HTTPS deployment URL.
  2. Sign in with your named address that appears in the administrator list.
  3. Confirm that the application opens the Admin workspace.
  4. Record the start of work when the organizational process requires a change or incident ticket.
  5. Sign out and close the browser profile when the work is complete.
Local development mode Local/demo mode may use a selected demo identity and more permissive backend behavior. Do not treat it as a production access-control check or audit record.

3.2. Operator sign-in

The Operator role always requires O authority. The identity may be a designated Firebase user or the bootstrap Operator account created during deployment. The server-side bootstrap token is valid for no more than eight hours and is stored in browser session storage.

First bootstrap Operator sign-in

  1. Receive the one-time displayed Operator email address and password through the approved secret-transfer process.
  2. Sign in over HTTPS. Insecure HTTP is accepted only when explicitly enabled for local development.
  3. Confirm that the application opens the Operator workspace.
  4. Configure and test the permanent Firebase access first, then handle the bootstrap credential under the organization's secret policy.
  5. After expiry or a 401/403 response, start a new session; do not attempt to recover the token from browser storage.
Bootstrap credential Deployment does not store the generated password in plaintext; only its digest is written to the secret file. The once-displayed password may appear in terminal or installation logs, so access to those logs must be restricted. Recovery of a lost credential is a host-operator task.

3.3. Access failure

Symptom Admin/Operator action Escalation
The normal application opens instead of the privileged workspace Sign out, verify the identity and email address, then sign in again. Operator verifies the administrator list or O authority.
401/403 response and session termination Do not repeat the action in a loop; sign in again. For recurrence, investigate identity, clock synchronization, and backend state.
The Admin side menu is disabled Check network state; do not treat pending changes as saved. Host/network operator if connectivity does not recover.
The final administrator address was removed Do not attempt an ad hoc database change outside the web interface. Immediately involve the Operator and host operator under an approved recovery procedure.

5. Reports and moderation

The Reports panel lists unresolved and resolved cases. Its detail view can show the reporter, time, reason, description, source quotation, subject member, and source context.

Investigate a report

  1. Open Admin → Reports.
  2. Select the Unresolved filter and open the case details.
  3. Reconcile the reporter, subject user, time, reason, details, and source context.
  4. For a chat report, open chat review; for another source, use item preview.
  5. Decide whether no action, a warning, or a block is appropriate. The organizational incident process takes precedence for severe, immediate risk.
  6. Perform the approved action, then mark the case resolved.
  7. Verify the result and record the rationale in the external case/audit register.

Decision guide

Situation Least proportionate action Required verification
Unsubstantiated or incorrect report Do not sanction; close the review. Document the source and report reason.
First correctable behavior issue Warning in the support chat. The message is specific, factual, and tied to policy.
Repeated or serious violation Block when the organizational policy permits it. Record the ID, evidence, approver, and rationale.
Suspected threat, unlawful content, or security incident Preserve evidence and escalate immediately; apply only approved mitigation. Incident lead and legal/privacy decision.

Warning

Send a warning

  1. Choose Warn from the report detail.
  2. Verify the target user and, for a chat report, the highlighted message.
  3. Edit the required warning text; do not include unnecessary personal data.
  4. Send the message and wait for confirmation.
  5. Use View chat for subsequent review of the support conversation.

Block and unblock

Block a user

  1. Confirm that the target user and report belong together.
  2. Select Block and read the confirmation dialog.
  3. Verify the support message and approval for the decision.
  4. Confirm the block and wait for the success response.
  5. Open Blocked users and verify the new state.

Unblock a user

  1. Open Blocked users.
  2. Identify the user; review the support chat and the unblock approval.
  3. Select Unblock.
  4. Verify that the user is no longer listed and record the result.
“Resolved” does not automatically mean sanctioned Resolving a report changes its review workflow state. Warning, blocking, and unblocking are separate actions; always verify that the intended enforcement action actually occurred.

6. User feedback

The Feedback panel manages unresolved and resolved entries. Details include subject, description, category, user, and submission time. Recognized categories are Bug report, Feature request, UX improvement, Performance, and General.

Process feedback

  1. Open Admin → Feedback.
  2. Select Unresolved, then read the full subject and description.
  3. Verify the category, submitter, and time; create an external development or support ticket when necessary.
  4. Select Mark solved only after the organization's processing requirement has been met.
  5. Use Mark unresolved to reopen an incorrectly closed item.
Functional boundary The verified interface has no assignment, internal comment, export, or development-ticket integration. Handle these in the organization's external workflow.

7. Support conversations and shared help views

Support chat

The Admin chat is intended for service/support conversations. A warning initiated from a report enters the same support context and can be reviewed later.

  • Always verify the conversation's target user.
  • Communicate only data necessary to resolve the case.
  • Never request a password, private key, service-account JSON, or payment secret.
  • Escalate threatening, legal, or privacy-sensitive content; do not improvise.

Shared help view

Report details can create a short-lived tokenized /admin/help/<token> link to the reported member's or source's application view. The server issues the token with a 24-hour lifetime.

Use a help link safely

  1. Create the member-view or source-view link from report details.
  2. Open it in an approved Admin work environment and verify that it shows the intended context.
  3. Do not paste it into public channels or free-text tickets, and do not capture unnecessary screenshots.
  4. Close the view after review. If disclosure is suspected, treat the 24-hour validity window as an incident risk.
Bearer-style access Possession of the link may be sufficient to resolve the shared target. The verified Admin UI has no manual token-revocation action; immediately escalate an accidental disclosure to security/privacy.

8. Help, legal, and explanatory content

The Content editor manages four content types: Help, Privacy, Terms, and Explanations. Content is maintained in English (EN) and Hungarian (HU). Explanations are bound to a predefined application screen.

Revision model

  • Saving creates a new inactive revision; it does not overwrite the active revision directly.
  • Editing an existing revision also creates a new version and carries its base-revision ID as trace data.
  • Activation is separate. One revision is active per type, language, and—where applicable—screen context.
  • The server sanitizes HTML, may omit empty sections, and makes colliding section IDs unique.
  • Create, activate, and delete operations produce backend audit records and telemetry events.

Create a content revision

  1. Open Admin → Content.
  2. Select the content type and language; for an explanation, select the target screen.
  3. Start a New revision or open an existing revision for editing.
  4. Enter the title, summary, description, header color, and sections.
  5. For each section, verify its label, icon, blurb, sanitized HTML, image, and panel span.
  6. Save and verify that the revision is inactive and has a new version number.
  7. Obtain content approval—and legal/privacy approval for legal content—before activation.

Activate a revision

  1. Open the approved inactive revision and compare it with the currently active version.
  2. Verify the type, language, screen context, and version.
  3. Select Activate.
  4. Open the user view and verify headings, sections, links, images, and responsive layout.
  5. Record the approver, time, old/new revision, and verification result.
Privacy activation Activating a privacy revision can establish a new consent boundary and require users to accept it again. Legal/privacy approval, support readiness, and user-flow testing are mandatory before activation.

Delete a revision

  1. Confirm the target revision ID and language.
  2. Check whether it is active. Delete an active revision only with an approved rollback plan.
  3. Select Delete and confirm.
  4. Reload the list and verify the active revision in the user view.
Automatic fallback activation When an active revision is deleted, the backend can automatically activate the newest remaining revision. Deletion is therefore not a “disable content” operation; always verify which earlier version became active.
Concurrent editing limitation The base-revision ID provides traceability, but the verified implementation does not provide complete optimistic locking or a visual merge workflow. Assign only one editor to a given content item at a time.

9. Article management

The Article editor manages English and Hungarian posts. Filters are All, Featured, Published, Drafts, and Trashed. An article can contain a title, excerpt, image carousel, and sanitized article HTML.

Create and publish an article

  1. Open Admin → Article and select the language.
  2. Start a new article; enter the required title, excerpt, images, and article HTML.
  3. Use preview and verify images, links, and layout.
  4. Save. The result is a draft that is neither published nor featured.
  5. On the card, select Publish separately and confirm.
  6. Verify the result in the user-facing article list.
  7. If required, mark only a published article as Featured.
Republishing is required after editing The editor's save request stores an article as a draft with both published and featured set to false. Editing and saving a published article can therefore remove it from the live interface; publish the approved version again as a separate action.

Unpublish, trash, and restore

  • Unpublish: removes the published state and clears featured status.
  • Move to trash: soft-deletes the article and clears published and featured status.
  • Restore: returns it from trash as an unpublished, unfeatured draft; publish separately.
  • Feature: is available only for a published article.
Audit limitation The backend maintains modification data and save/delete/restore telemetry, but the verified article interface has no browsable, immutable revision history comparable to governed Help or legal content. Preserve approval evidence in the external change ticket.

10. Platform parameters

The Params panel manages platform behavior in seven sections. A save creates a complete new active configuration version and makes the previous active version inactive. The change can queue affinity recomputation and generate an administrator notification.

Section Examples of affected settings Primary risk
Matching rating, evidence, and owner-context multipliers matching order and quality
Profile profile-field rules, impression and trait multipliers profile and affinity calculations
Events affinity, boost, capacity, and host confidence event recommendations and capacity
Assets affinity, boost, requests, and freshness asset recommendations and request handling
Discovery distance multiplier, maximum meters, and strategy result radius and geographic relevance
Notifications send window, workers, retries, backoff, and multicast/topic thresholds notification latency, load, and duplication
Jobs debounce, polling, batch, lease, processing cadence, and account-purge window background load, latency, and retention boundary

Change a parameter

  1. Open Admin → Params and expand the target section.
  2. Record the active version and baseline value of every field to be changed.
  3. Review impact with product, data, and operations owners; include the host operator for significant capacity risk.
  4. Change only the approved value; never try to bypass a read-only field.
  5. Save the configuration and record the new version.
  6. Observe affinity recomputation, jobs, monitoring, and user behavior.
  7. Use section-level rollback when results deviate from the approved expectation.

Restore a section from an earlier version

  1. Open the section's History.
  2. Identify the approved earlier version, modifier, time, summary, and values.
  3. Select Switch to this version.
  4. Verify that a new active configuration version was created with the selected section's earlier values.
  5. Repeat impact verification.
Rollback creates a new version A section rollback does not reactivate the old document. It creates a new active configuration version from that section's earlier values. Rolling back several sections is not atomic; manage the interim mixed state in the change plan.

11. Scheduled jobs

The Jobs panel shows scheduled-process state, last and next run, pending count, runtime progress, detail, and history. State can update over WebSocket and, during a run, by short-interval polling.

Status Meaning Administrator action
Ready Available to run or awaiting its next scheduled slot. Normal observation.
Running Execution is in progress. Do not start another manual run; observe progress.
Failed The most recent run failed. Review detail/history, correlate logs, and assess incident impact.
Missed A scheduled run did not occur. Investigate schedule, downtime, and backlog.
Suspended The process is paused. Resume only with approval and after assessing accumulated work.

Processes supplied in the baseline package

The following list reflects the released seed configuration. The configuration displayed in the live panel is authoritative.

Process Purpose Typical baseline interval
Matched rooms Assign accepted members to generated rooms using affinity and prior-meeting signals. 1,440 minutes; manual run enabled
Auto inviter Process eligible invitation/wait-list candidates. 120 minutes
Tournament review Review tournament stage states periodically. 30 minutes
Event counter expiry Handle counters associated with past events. 5 minutes
Checkout basket cleanup Remove expired checkout-basket drafts. 1 minute
Notification outbox Process delivery of pending notification intents. 1 minute
Affinity recompute Execute queued affinity recomputations. 1 minute

Change a schedule or job parameter

  1. Open the process detail and verify status, pending count, last/next run, and history.
  2. Pause the process when necessary, but first calculate the expected backlog and user impact.
  3. Edit the start time, fixed interval and unit, and any exposed process parameters.
  4. Save, reload the detail, and verify the next run time.
  5. After resuming, observe the first complete run and confirm that the pending count declines.

Manual run

  1. Verify that the process is enabled, not running, and that Run is available.
  2. Identify the target workload and any potentially irreversible impact.
  3. Start the run and monitor progress and history until completion.
  4. Do not retry blindly after failure; inspect the detail and escalate.
Manual Matched rooms run In the released baseline this is the process with manual execution enabled. It can modify user and event-group assignments; run it only for an approved event scope, with a captured baseline and result verification.

12. Statistics, monitoring, and affinity graph

Stats

Stats is a read-only panel with an explicit Refresh action. It can show KPIs and health, timelines for active users, registrations, ratings, events/assets, messages, and moderation, and aggregated network-quality, community, bridge-user, event-type, segment, city, and topic data.

Investigate a statistical anomaly

  1. Open Admin → Stats and select Refresh.
  2. Record the observation time, metric, trend, and comparison baseline.
  3. Compare at least two related metrics; do not intervene on a single KPI alone.
  4. Correlate the change with configuration, job, release, and incident times.
  5. Escalate suspected data-quality issues; do not “correct” product parameters before validating the measurement.

Monitoring

Monitoring displays aggregate node, edge, and status metrics filtered by category. Verified filters are All, Watch, Domains, Notifications, and Background; health is shown as Healthy, Watch, or Alert.

Snapshot behavior The verified panel has no separate refresh control or proven timed auto-refresh. Close and reopen it to issue a new query. Correlate a persistent alert with server-side metrics and logs.

Affinity graph

Graph opens a full-screen, read-only 3D view. It can show forest/component overviews, members, links, components, and isolated members. Large data sets load progressively.

Use the graph

  1. Open Admin → Graph and wait for the data-loading indicator to complete.
  2. Pan with the left mouse button, rotate with the right button, zoom with the wheel, and pan by steps with the arrow keys.
  3. Select a forest/component, then a member badge to view the profile and strongest links.
  4. Use Link range to hide links outside the selected strength range; for a selected member, set link depth from 1 to 3.
  5. Select Reset to return to overview.
Not evidence of intent An affinity link or visual proximity is a computed relationship. It cannot serve by itself as evidence for moderation, legal, or user decisions.
Layout rebuild A layout-rebuild backend endpoint exists, but the interface has no control for it in the Admin graph panel. Do not invoke it manually from the browser; escalate it as an approved technical change.

13. Operator workspace

The Operator page manages network and deployment duties for the installed node. Its main actions are Updates, Node registration, Claim share, Configuration, and Revenue; Community is available from the side rail. The leaderboard provides Founder, Claimed, and Unclaimed views and a deployment list for each group.

Scope of Operator actions These actions can change identity, external network connectivity, authentication, TLS, payment routing, and installed software. Access to the Operator workspace does not replace change approval or host-side recovery readiness.

Operator pre-check

  • The deployment's unique identity and environment are confirmed.
  • System time, HTTPS, and network connectivity are healthy.
  • No other Operator change is running on the same node.
  • Affected secrets originate from an approved secret store.
  • The host operator is available for a high-risk change.
  • The recovery point, owner, and decision threshold are documented.

14. Node registration and measurement delivery

Node registration shows lifecycle state and the selected registry URL. In real mode, the candidate must use HTTPS. The current interface permits selection only from the registry catalog supplied by the server; the text field is read-only and there is no manual URL entry.

First registration

  1. Open Operator → Node registration.
  2. Verify the current lifecycle and any selected registry.
  3. Select the approved registry from the catalog.
  4. Independently verify the registry scope and TLS/network expectation.
  5. Select Register node.
  6. Wait for Registered, refresh the panel, and verify the leaderboard mutation.
The actual 1.0.0 interface Although the backend has separate inspect and confirm endpoints, the released Operator panel displays no “Inspect” or “Confirm” control. The documented UI process is catalog selection followed directly by Register node; do not prescribe controls that are not visible.

Switch registries

  1. Record the current registry URL, scope, state, and associated network/group bindings.
  2. Verify the new catalog registry and scope through an independent channel.
  3. Select the new registry and start registration.
  4. If a partial-switch error appears, treat the old connection as removed and the new one as not established.
  5. Do not retry without control. Verify status, network, and registry, then register to the approved target.
Registry switching is not atomic When the target differs, the client disconnects the existing binding before registering with the new registry. If the second step fails, the node remains unregistered. Switch only with an accepted outage and recovery plan.

Disable the connection

  1. Confirm that the intended target is the current registry connection.
  2. Record associated node, group, measurement, and revenue-delivery state.
  3. Select Disable connection.
  4. Verify Disabled and the expected restrictions on Operator functions.

Measurement synchronization

For a registered node, the panel shows delivery state and counts of materialized, submitted, accepted, pending, and blocked measurement reports. Blocked reports are listed and can be requeued individually.

Synchronize measurements and requeue a blocked report

  1. Verify that the node is registered and delivery is not Busy.
  2. Select Synchronize measurements.
  3. Compare the materialized, submitted, accepted, pending, and blocked counts.
  4. For a blocked item, read its period, revision, failure code/message, action count, and attempt count.
  5. Select Queue resend only after correcting the underlying cause.
  6. Verify that the item becomes pending and is accepted by a subsequent synchronization.

15. Ownership claim, leaderboard, and community

Company ownership claim

A registered node can be claimed through company verification or with a temporary client code from an already verified Operator group. The company route requires legal name, registration number, jurisdiction, registered address, website, verification-contact name/role/email, and an authority attestation.

Submit a company claim

  1. Open Operator → Claim share and select Company details.
  2. Verify that the node is registered and the verification backend is available.
  3. Enter company and contact data from authoritative registration sources.
  4. Select the required attestation only with verified authority to represent the entity.
  5. Select Claim this node and record the status.
  6. Do not resubmit while Under review. The screen sends no email: follow its contact instruction; approval occurs at the registry, outside this web UI. Escalate Rejected or Suspended status.

Issue and redeem a client code

Issue a client code

  1. Use the header client-code action only on an active, approved/verified node that belongs to a group.
  2. Record the displayed expiry, but do not copy the code itself into a log.
  3. Use Copy code and transfer it to the target Operator through an approved secret channel.
  4. Treat it as consumed after successful redemption; do not redistribute it.

Redeem a client code

  1. On the target node, open the claim panel and select Client code.
  2. Paste the received code and verify that the target node is registered.
  3. Select Claim this node.
  4. Verify the provisional group membership and leaderboard mutation. Investigate the cause before requesting a replacement code after failure.
Client code is a short-lived secret The code can attach a deployment to an Operator group. Give it only to the designated recipient; never place it in chat, a ticket, screenshot, or source code.

Leaderboard

The leaderboard and group deployment list are read-only snapshots. Displayed share, weight, claim, and eligibility state are for verification. For discrepancies, record the snapshot period and deployment/group ID, then escalate to the registry.

Community and announcements

Community displays available provider links and registry announcements. An announcement can show kind, severity, status, publication/expiry time, details, and—for an update—signature and compatibility metadata.

Community-state limitation The remote HTTP data source does not support changing community availability; treat the panel as read-only in production. Open a provider link only when it is available and uses HTTPS.

16. Software updates

Updates shows the current and available versions, the most recent update, and the progress of any active job. Check for updates requests a new registry snapshot; Update deployment is enabled only for an installable newer release.

Security model

  • Only an available, compatible, and newer release is accepted.
  • The registry announcement's signing key, locally pinned release key, and package signature must verify.
  • The backend downloads over HTTPS, verifies size and SHA-256, and stages the package in local state.
  • A privileged local update helper performs the package installation; this is a host-side trust boundary.
  • The browser follows job events and maps lower-level host phases to Checking, Downloading, Verifying, Installing, Completed, or Failed.

Perform an update

  1. Create an approved change ticket. Reconcile the target version and compatibility/signature data shown in the Community update announcement. Obtain expected downtime and backup requirements separately from an approved release source.
  2. The host operator verifies a current backup, tested recovery point, free storage, and the privileged update helper.
  3. Open Operator → Updates and select Check for updates.
  4. Compare the current and available versions with the approved release.
  5. Select Update deployment. Do not close the change merely because download or verification completed.
  6. Follow progress to Update completed; expect temporary loss of connectivity during installation/restart.
  7. After reconnection, verify the current version, sign-in, Admin/Operator routes, and designated smoke tests.
  8. Record the job ID, target version, result, duration, and verification.
Panel phase Interpretation Action
Checking Validating the signed manifest and prerequisites. Wait; investigate network/registry if prolonged.
Downloading Package download in progress. Do not start another job; observe the byte counter.
Verifying Digest/signature verification and local handoff. Never bypass verification after failure.
Installing Waiting for the host helper, backing up, installing, or restarting. Keep the host operator ready; do not interrupt.
Completed The job completed. Verify version and function.
Failed May represent host states Failed, Rejected, or Recovery Required. Stop; inspect job/helper logs and make a recovery decision.
Failed is not sufficiently specific The web view can collapse several host terminal states into “Failed.” In particular, never retry or start another update after Recovery Required until the host state and backup have been examined.

17. Deployment configuration

Configuration manages deployment branding, privacy contact, administrator email addresses, social links, payment provider, Firebase integration, and HTTPS. Each section exposes a separate save action, but a save request submits the current complete configuration draft. Review every pending field in the panel before saving any section.

Branding, privacy contact, and social links

Save lower-risk configuration

  1. Open Operator → Configuration.
  2. For branding, verify product name, logo image, logo-replacement index, and theme. The zero-based index identifies the product-name character replaced by the logo; the default index 0 replaces the M in MyScoutee. Use -1 to show the full product name without a logo in the wordmark; the configured logo remains available to other branded surfaces.
  3. For privacy, enter the data-controller name and public privacy email address.
  4. For a social link, verify provider, label, HTTPS URL, icon, and handle; no more than 12 links can be added.
  5. Save the target section, then verify public presentation and links in a separate browser session.

Administrator email addresses

A authority is tied to addresses in the administrator list. An address is not a password; the user authenticates through Firebase. An authority change becomes effective on the next sign-in or authentication-token refresh.

Add or remove an administrator

  1. Open the administrator section and preserve the currently approved list in the change record.
  2. Verify the address to be added or removed through two sources; use a named organizational address.
  3. Maintain at least one other tested Admin account independent of the executor.
  4. Edit the list and select Save administrators.
  5. After signing out and back in, the new Admin verifies /admin. For removal, verify in a new session that the old identity no longer enters.
Lockout risk Never remove the final functioning administrator address. The verified UI has no break-glass Admin control; lockout requires Operator and host-operator recovery.

Payment provider

The panel selects an available provider and manages the public base URL, provider-specific merchant account, and secret credential. An existing secret cannot be read back; the UI shows only a masked or configured state.

Register or update payment configuration

  1. Reconcile the environment, merchant, and callback/public URL with the provider portal and change record.
  2. Select the provider and enter the approved public base URL and, where requested, merchant email/account.
  3. Paste the credential directly from the approved secret store; do not log it.
  4. Select Register payment or Update payment and wait for confirmation.
  5. Run the provider-approved low-value or sandbox end-to-end test; verify webhook and accounting results.
Remove provider Selecting no provider creates a Remove payment action. Do so only after checking active payment flows and open refunds.

Firebase

The Firebase section manages public client configuration—project ID, API key, auth domain, storage bucket, messaging sender ID, app ID, optional measurement ID, and VAPID key—and separate authentication and messaging service-account credentials. Save, two capability tests, and activation are distinct.

Introduce Firebase configuration

  1. Confirm that every public value and both service accounts belong to the same approved Firebase project and environment.
  2. Complete the public fields and paste the authentication and messaging credentials.
  3. Select Save Firebase. Test controls become available only for saved, clean configuration with registered credentials.
  4. Run Auth Test.
  5. Allow notifications in the test browser and verify its service worker. Optionally enter an additional test-device token, then run Message Test.
  6. Select Activate Firebase only after both successful tests and complete public-client fields.
  7. In a separate browser, verify sign-in, token refresh, push-permission flow, and a test notification.
Fail-closed behavior A failed capability test can deactivate the live Firebase revision. Test only in a maintenance window with a rollback plan and alternative Operator access.
Secret handling Existing service-account credentials cannot be read back, and the client clears credential fields from the draft when the configuration panel closes. Recovery or rotation of the master key used for server-side secret encryption is a host-operator procedure.

HTTPS

HTTPS can be enabled or disabled. Automatic mode uses a domain, contact email, and automatic renewal. Manual mode uses a domain, certificate, and private key. Separate domain and certificate tests precede a save job.

Configure HTTPS

  1. With the host operator, verify DNS records, public reachability, proxy/port routing, and the change window.
  2. Enable HTTPS, enter the domain, and select Automatic certificate or Certificate and key.
  3. In automatic mode, enter a monitored contact email and choose automatic renewal. In manual mode, paste the complete certificate chain and matching private key.
  4. Run Test domain, then Test certificate.
  5. Only after successful tests, select Save HTTPS and follow the job state.
  6. With an independent client, verify HTTPS, certificate chain, name, expiry, redirects, and Admin/Operator sign-in.
Private key Never put a private key in a ticket, chat, screenshot, or version control. After an unsuccessful or unknown save result, reload authoritative state before attempting any further action; do not paste the key again automatically.

18. Revenue and settlement view

Revenue can show the ruleset and commission rate, revenue metrics by currency, a projected timeline, asset categories, delivery state, blocked reports, and settlement snapshots.

Delivery

Counters show materialized, submitted, accepted, pending, and blocked reports. For a blocked report, the panel shows period, revision, failure message/code, attempt count, affected currencies, and failure time.

Synchronize revenue delivery

  1. Select the currency and record the ruleset version and commission rate.
  2. Compare period, payment, refund, net, and commission metrics with the approved payment-provider report.
  3. Select Synchronize delivery.
  4. Verify changes to accepted, pending, and blocked counts.
  5. Select Requeue report for a blocked report only after correcting its underlying cause and data.

Settlement snapshots

The view can show period, currency, revision, monthly network pool, group allocation, share, trailing commission basis, indicative network/group values, three-month averages, growth, acceleration, adjustment, multiplier, ruleset, and accepted time.

Nonbinding The panel explicitly presents settlement data as indicative and nonbinding. It does not replace an invoice, provider statement, tax document, or accounting record and is not sufficient by itself for a payout decision.
  • Always record currency, period, revision, and ruleset.
  • Do not aggregate different currencies without an exchange-rate source and time.
  • Do not omit superseded revisions from final reconciliation.
  • When escalating a discrepancy, include provider, registry, and local report IDs together.

19. Change management and audit

Built-in auditability differs by function. Governed content has the strongest revision audit, and parameters have version history. For several moderation, article, Operator, and configuration actions, application state, telemetry, or a job ID is not a complete organizational audit trail. An external change/case register is therefore mandatory.

Data minimization Do not store full chats, help tokens, client codes, private keys, credentials, payment secrets, or device tokens as audit evidence. A unique object ID and the necessary masked evidence are sufficient.

Minimum audit record

Field Required content
Identification ticket/incident, environment, deployment, and target object's unique ID
Actors requester, executor, and verifier/approver
Time start, execution, completion, and time zone
Change old/new value or state; version, revision, or job ID
Rationale and impact business/technical reason and affected users, data, and service
Evidence success/failure state and verification result, without secrets or unnecessary personal data
Rollback plan, decision threshold, execution, or reason for not executing

Built-in audit sources by function

Function Built-in trace Required supplement
Help/legal/explanation content revision plus create/activate/delete audit and telemetry approver, comparison, and user-view test
Parameters version, modifier, time, summary, and values impact measurement, approval, and multi-section order
Scheduled job runtime state, history, and execution detail change rationale, schedule before/after, and backlog
Update/HTTPS durable job and event state backup, approval, host-helper evidence, and smoke test
Moderation and Operator configuration object state and partial telemetry decision rationale, approver, and previous/new state

20. Incident response and escalation

Severity guide

Level Example Immediate action
S1 — critical complete outage; Admin/Operator lockout; Recovery Required; authentication or private-key incident; mass incorrect blocking stop changes; immediately engage the incident lead and host operator; preserve evidence
S2 — high widespread Firebase/push or payment failure; lost registry connection; incorrect legal-content activation mitigate and engage relevant service, privacy, legal, or finance owners
S3 — medium persistent job failure; blocked measurement/revenue reports; monitoring alert with partial impact diagnose and use a controlled retry or change window
S4 — low single feedback item; cosmetic content defect; transient snapshot discrepancy normal casework and planned correction

Immediate decision tree

Failure after a privileged action

  1. Is a write or job still in progress? Do not start a second action; reload state and determine the unique job/revision result.
  2. Does it affect access, secrets, money, legal content, or many users? Classify at least S2 and involve the designated owner.
  3. Is there Recovery Required, an outage, or suspected corruption? Stop; a host operator and incident lead are required.
  4. Can the UI restore it safely? Use only an approved, proven rollback action.
  5. Is there no UI rollback? Do not call the API manually or edit the database; escalate into the operations procedure.

Escalation package

  • Environment, deployment, and affected function.
  • Exact UTC/local time and time zone.
  • User, report, revision, job, group, or deployment ID.
  • Previous and current state and the button/action executed.
  • Exact error text/code, with secrets removed.
  • User, privacy, financial, and availability impact.
  • Mitigation performed and risky attempts explicitly not performed.
Do not create a second failure After an unknown save, registry switch, block, update, Firebase activation, or financial requeue, query authoritative state first. Pressing the action again is not a recovery procedure.

Start of shift

  • Correct environment and named account.
  • HTTPS and network state healthy.
  • Open S1/S2 incidents handed over.
  • Active job, update, and HTTPS state reviewed.
  • Change windows and approvers known.

End of shift

  • No save or job has an unknown outcome.
  • Unresolved cases and escalations handed over.
  • Audit/change records complete.
  • Clipboard and temporary local secrets cleared.
  • Admin/Operator sessions closed.

Moderation

  • Target user and source verified.
  • Full context reviewed.
  • Action proportionate and approved.
  • Message factual and data-minimized.
  • State and rationale recorded.

Live content

  • Type, language, and screen correct.
  • Preview, links, and images verified.
  • Legal/privacy approval available.
  • Old and new revisions recorded.
  • User view tested after activation.

Configuration

  • Baseline and target values recorded.
  • Impact, capacity, and rollback assessed.
  • Four-eyes review complete.
  • Only approved fields changed.

Update/HTTPS/Firebase

  • Alternative access and host readiness.

23. Workspace administration, Feedback and connections

Work and Community responsibilities

Select the intended workspace and group before taking an administrative action. Work campaigns have draft/published/trash states and related events with their own recipients and capacity. Community cases have affected members, provider invitations, quotations, appointments and a task board. Follow the controls available to your current group role; application Admin access does not replace a case owner's decision.

For recurring Community tasks, review the affected audience, next due time and pause/resume state. A scheduled task, generated case, service appointment and board task have separate lifecycles. Review the specific record before changing its state.

Central Feedback and protected help

Product suggestions and bug reports in chapter 6 are separate from event/service Feedback. Event and service responses use central Feedback ownership, labelled criteria and read-only reopening after submission. The displayed badge and counters summarize the owner's records; they are not editable numeric scores.

Role guides and notifications follow the active role and available surface. System-provided guide content is protected. Use the governed-content editor's allowed revision workflow; do not delete or overwrite protected system definitions to change a label or dismiss an introduction. Introduction dismissal is separate from consent.

API/MCP access

Review API keys, manual MCP clients, OAuth permissions and the main MCP link in the existing API settings. Blocked denies access; Write permits supported organizing commands; Read adds queries; Full adds Events. Each MCP client's effective pack is capped by the main MCP pack. Confirm the nested selector, then save the parent form; closing a draft is not a permission change.

Administrator and Operator queries remain scoped to the signed-in role and node. Full access does not authorize personal ratings, feedback, ballots, invitation responses or offer decisions. Revoke a connection through its own settings entry; browser logout is not OAuth revocation. Consult the MCP User Guide for setup.

Signed updates

The current full installer is 1.4.1. Review its signed catalog, compatibility, backup and verification requirements in the Operations Manual before approval. Publication of the package does not prove an automatic updater or rollback drill.
