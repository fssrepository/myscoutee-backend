1. Purpose and Scope

This manual provides repeatable, verifiable, and security-conscious procedures for installing and operating a MyScoutee 1.0.0 production instance.

In Scope

  • Debian/Ubuntu-style amd64 hosts that use apt;
  • the packaged stack running on Docker Engine and Docker Compose v2;
  • Nginx, the Java API, MongoDB, Redis, MinIO, and the isolated Explore registry;
  • startup, shutdown, health checks, log analysis, and capacity monitoring;
  • backup and restore of MongoDB, configuration, MinIO, and the deployment registry;
  • operation of TLS certificates, signed package updates, and registry connectivity;
  • security, troubleshooting, and removal procedures.

Out of Scope

  • installation and SQLite recovery of the separate Go registry service;
  • end-user or administrator use of application features;
  • provider-specific high-availability designs, managed databases, layer-7 load balancers, CDNs, or external backup products beyond the qualified single-VM mappings in Chapter 5;
  • non-amd64 architectures, Kubernetes, or multi-node MongoDB topologies;
  • guaranteed SLA, RTO, RPO, or hardware sizing.

Source Stack and Packaged Stack

The repository file server/docker-compose-prod.yml defines a buildable source-production environment with relative development data paths and pull_policy: build. The installed package deploys packaging/compose/docker-compose.production.yml as /opt/myscoutee/server/docker-compose-prod.yml, with fixed host directories and pull_policy: never. When operating production, use the commands under /opt/myscoutee specified in this manual. The two Compose variants are not interchangeable.

Separation of Explore and the Real Registry

The Explore registry is an internal demo service with separate SQLite data, a separate signing key, and separate Java client state. It cannot be selected as the Operator's real registry and shares no state with the external registry.

4. Requirements and Preparation

Supported Installation Platform

  • An apt-based Debian/Ubuntu system with systemd service management;
  • amd64 architecture for the released 1.0.0 package;
  • root or sudo privileges;
  • Docker Engine and Docker Compose v2;
  • a public domain and DNS when Internet-facing TLS is required;
  • inbound TCP 80 and 443, while preserving a source-restricted SSH path through both the guest and provider network controls;
  • outbound access at minimum for missing MongoDB/Redis images, certificate issuance, and approved external providers.

System Requirements and Initial Sizing

The following values are conservative planning baselines for the packaged six-container stack. They are not measured capacity limits, user-count guarantees, or an SLA. Use the small-deployment column only for evaluation, commissioning, or a low-traffic deployment; use the production column as the initial production size and validate it with representative load, data-retention, media, backup, and restore tests.

Approximate host sizing baseline
Resource Small deployment baseline Recommended production starting point Qualification note
CPU 4 amd64 vCPUs 8 amd64 vCPUs Increase for concurrent API work, scheduled jobs, imports, backup compression, or restore windows.
Memory 8 GiB RAM 16 GiB RAM Keep at least 25% headroom under representative peak load. Swap is an emergency buffer, not a replacement for RAM.
Persistent SSD storage 80 GiB 160 GiB or more Includes the OS, Docker images, MongoDB, MinIO media, logs, update staging/cache, and local backup workspace. Retention and uploaded media normally determine growth.
Free working headroom to maintain 20 GiB 40 GiB or 25% of the filesystem, whichever is larger Preserve additional working space before backup, restore, or update operations; do not plan to run a production filesystem close to full.
Backup capacity Separate off-host target for at least one complete backup Encrypted off-host target sized for the approved retention window and restore testing Calculate from actual MongoDB, MinIO, configuration, registry, and key material. Infrastructure snapshots remain additional controls only.
Network Stable address, canonical DNS, and connectivity for the approved providers Stable public address and bandwidth sized from measured browser, API, media, backup, and update traffic Latency, egress policy, upload size, and backup-window requirements matter more than the nominal link rate.

Baseline, Not a Guaranteed Minimum

The package sets no Java, MongoDB, Redis, or container memory limits, so a workload can exceed these values. Monitor CPU saturation, memory pressure, disk latency, filesystem usage, MongoDB growth, and backup duration from commissioning onward. Scale before sustained peak utilisation removes the required headroom. The update process also holds separate staging and root-cache copies and, by default, requires an additional 512 MiB free-space reserve for each copy beyond the signed artifact size.

Preinstallation Checklist

  • The supported host architecture and distribution are documented.
  • Time synchronization, DNS, and the hostname work correctly.
  • Disk allocation separately accounts for /var/lib, /var/cache, /var/log, /var/backups, and Docker storage.
  • Ports 80 and 443 are reachable through the firewall; port 27017 is not public.
  • The deployment domain and TLS mode have been approved.
  • A secure method is ready for recording the shown-once Operator credential.
  • Owners have been assigned for the backup target, off-host copy, retention, encryption, and restore testing.
  • The installation package source and SHA-256 digest have been verified.

Host Prerequisites and Optional Utilities

On a clean VM, install and test OpenSSH separately as described in 5.2. Install the product with apt; APT resolves the Docker Engine and Docker Compose dependencies declared by the Debian package. The following package-owned helpers become available only after package installation or explicit package extraction:

sudo /opt/myscoutee/packaging/scripts/install-vps-prerequisites.sh
sudo /opt/myscoutee/packaging/scripts/doctor-production.sh

install-vps-prerequisites.sh is an optional missing-utility helper, not the MyScoutee installer. doctor-production.sh checks only for the presence of commands; it does not verify the running stack, disk capacity, certificates, or backups.

5. Deployment Platforms, Public DNS, and Firebase Preparation

This chapter maps the supported MyScoutee host contract to common infrastructure products. Provider consoles create the VM, network, stable address, firewall policy, storage, and DNS records; they do not replace the MyScoutee package installer. The same released Debian package and the same operating procedures are used on every platform.

5.1. Runtime Boundary and Available Deployment Surfaces

The supported runtime is one amd64 Debian/Ubuntu guest with apt, systemd, Docker Engine, and Docker Compose v2. The package runs a stateful six-container stack, uses fixed host paths, and installs privileged local update and TLS workers. The host does not need Java because the Java runtime is contained in the packaged API image.

Infrastructure products that can provide the supported VM
Infrastructure surface Use for MyScoutee Provider resources
Google Cloud Compute Engine amd64 VM VPC subnet, firewall rules, reserved external IP, persistent disk, and Cloud DNS or external DNS
VMware vSphere Debian/Ubuntu 64-bit guest managed through vCenter or the vSphere Client Datastore-backed virtual disks, port group/VLAN, stable guest address, and upstream firewall, NAT, and DNS
OpenStack Nova amd64 instance managed through Horizon or the OpenStack API/CLI Glance image, tested flavor, Neutron network/security group/floating IP, Cinder storage, and Designate or external DNS

Firebase and Serverless Products Are Not the Runtime

Firebase supplies external authentication and push messaging for MyScoutee; it does not host this release. Firebase Hosting/App Hosting, Google App Engine, Cloud Run, GKE/Kubernetes, and generic shared web hosting are not drop-in targets for the Debian package because they do not provide the required single-host systemd, Docker Compose, persistent-path, and privileged-worker contract.

5.2. Common VM, Storage, and Network Contract

  • Select an approved amd64 Debian/Ubuntu image; do not select an Arm machine type or image.
  • Keep the VM clock synchronized and give the guest a stable address that survives an ordinary stop/start.
  • Begin with the Chapter 4 sizing baseline, then qualify CPU, RAM, disk performance, and capacity with release-specific load, retention, backup, and restore tests.
  • Provide persistent capacity for /var/lib, /var/cache, /var/log, /var/backups, and Docker storage before installation.
  • Encrypt infrastructure disks according to local policy, but retain MyScoutee logical backups and an encrypted off-host copy; a VM or volume snapshot is not a substitute for the application backup.
  • Preserve administrative access without exposing database, cache, object-store, API, or registry container ports.
Minimum network-policy intent for a directly exposed VM
Traffic Source or destination Policy Purpose
Inbound TCP 80 Internet Allow HTTP-to-HTTPS redirect, ACME HTTP-01, and the Operator domain test
Inbound TCP 443 Internet Allow Application HTTPS and secure WebSockets
Inbound TCP 22 Approved administrator CIDRs, bastion, VPN, or provider access proxy only Restrict Host administration and optional SSH forwarding
Inbound TCP 27017 Any external network Deny The package exposes the MongoDB proxy on host loopback only
Other container ports Any external network Deny Java, Redis, MinIO, MongoDB, and the Explore registry communicate on the private Compose network
Outbound DNS, NTP, and HTTPS Approved resolvers, time sources, image sources, ACME, Firebase/Google APIs, registry, update source, and configured providers Allow as required Name resolution, time, installation, certificates, authentication, messaging, and integrations

SSH Is Infrastructure Prerequisite, Not Product Installation

The MyScoutee package does not install or configure openssh-server, create a host-administrator account, add an SSH key, or open TCP 22. Prepare and test that management path through the provider console before relying on remote installation. On an approved Debian/Ubuntu guest, a typical host-side check is:

sudo apt install openssh-server
sudo sshd -t
sudo systemctl enable --now ssh
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Use a named non-root account with the required sudo authority and prefer key authentication. Obtain the SSH host-key fingerprint through the provider console or another independent channel, compare it on first connection, and keep console recovery available while changing SSH or firewall policy. Do not disable password login or root login until a second, key-authenticated session has succeeded.

The repository-qualified topology terminates TLS in the packaged Nginx container on the VM. A CDN or layer-7 load balancer that terminates TLS, changes redirects, or rewrites forwarded headers is a different design and requires separate qualification, including WebSocket, HSTS, health-check, client-address, and ACME behavior. A direct address, NAT, floating IP, or layer-4 pass-through is closer to the documented boundary.

5.3. Google Cloud Compute Engine Example

  1. Create or select the production Google Cloud project, region, zone, VPC, and subnet under the organization’s billing, IAM, audit, and retention controls.
  2. Reserve a regional static external IPv4 address. Do not publish DNS against an ephemeral address.
  3. Create a firewall target for the MyScoutee VM. Allow TCP 80 and 443 from the intended public sources, restrict SSH to the approved administration path, and add no public rule for TCP 27017 or internal container ports.
  4. Create a Compute Engine VM from an approved amd64 Debian/Ubuntu image. Map the Chapter 4 baseline to a machine type with at least 4 vCPUs, 8 GiB RAM, and an 80 GiB persistent SSD for a small deployment, or begin production qualification at 8 vCPUs, 16 GiB RAM, and 160 GiB. Increase storage for measured database, media, log, update, and backup retention.
  5. Attach the reserved address and use OS Login, IAP, a bastion, or approved SSH keys. The VM’s Google Cloud service account needs no broad Firebase role; grant only permissions required for separately selected Google Cloud agents or backup automation.
  6. Create the canonical DNS record described in 5.6, wait for public propagation, and verify that it resolves to the reserved address. Verify host-to-public-name reachability after the package and Nginx have started.
  7. Transfer the approved myscoutee_1.0.0_amd64.deb, verify its SHA-256 digest, and continue with Chapter 6. Take the first logical backup after commissioning; Compute Engine disk snapshots remain an additional infrastructure control only.

Do Not Confuse Google Identities

The human or automation identity that provisions Google Cloud, the service account optionally attached to the Compute Engine VM, and the JSON service-account credentials supplied to MyScoutee for Firebase are separate security principals. An attached VM service account does not replace the Firebase credentials expected by the current application interface.

5.4. VMware vSphere Mapping

  1. In vCenter or the vSphere Client, create a Debian/Ubuntu 64-bit VM from an approved template or ISO and attach it to the intended datastore and port group/VLAN.
  2. Assign vCPU, RAM, and virtual-disk capacity from the Chapter 4 baseline, then adjust it from load-test and retention evidence. Install the approved guest tools package when required by the local vSphere operating standard.
  3. Give the guest a stable address through static guest configuration or a controlled DHCP reservation. Use the vSphere console to install and validate OpenSSH, provision the named host-administrator account and public key, and record the guest’s SSH host-key fingerprint.
  4. Prefer a private management port group reached through the organization’s VPN or bastion. Permit TCP 22 from only that management source in the guest firewall and in any NSX distributed firewall or upstream firewall that protects the VLAN.
  5. If the guest must be reached through NAT, create a narrowly scoped DNAT/VIP rule on NSX Edge or the upstream firewall/router, for example external TCP 2222 to the guest’s TCP 22, and permit only the approved administrator CIDR. A vSphere port group connects the virtual NIC; vSphere alone does not create the required Internet NAT or perimeter-firewall policy. Set REMOTE_HOST and REMOTE_PORT in the client tools to the externally reachable address and port.
  6. From the actual management workstation, compare the independently obtained host-key fingerprint and verify ssh -i /path/to/key -p 2222 host-admin@198.51.100.20. Remove temporary broad rules after this test; do not expose SSH to 0.0.0.0/0.
  7. For public application access, separately configure the upstream firewall and one-to-one NAT or virtual IP so TCP 80 and 443 reach the same guest. Point public DNS at that stable address and verify NAT reflection/hairpin behavior as described in 5.6.

Do not clone a running or previously registered production VM to create another deployment. That duplicates MongoDB data, the registry signing identity and receipts, the deployment master key, and provider credentials. Move or restore one logical deployment as a controlled recovery unit. vSphere snapshots are short-lived infrastructure rollback aids, not database-aware MyScoutee backups.

5.5. OpenStack Mapping

  1. Select an approved amd64 Debian/Ubuntu Glance image and map the Chapter 4 CPU, RAM, and SSD baseline to a Nova flavor and Cinder-backed boot volume. Select the tenant network, inject an approved OpenStack key pair at server creation, and confirm the image-specific non-root login name.
  2. Create a dedicated Neutron administration security group with one ingress TCP 22 rule whose remote CIDR is the administrator workstation, VPN, or bastion—not the entire Internet. Attach that group to the instance port. Create separate public-web rules for TCP 80 and 443; do not add TCP 27017 or internal container ports.
  3. For a directly administered instance, allocate a floating IP from the approved external network and associate it with the server. If policy requires a private instance, do not allocate a floating IP: connect through a VPN or bastion and restrict TCP 22 to that private source or security group.
  4. Equivalent OpenStack CLI operations are: 
    openstack security group create myscoutee-admin
openstack security group rule create \
  --ingress --ethertype IPv4 --protocol tcp --dst-port 22 \
  --remote-ip 203.0.113.10/32 myscoutee-admin
openstack server add security group myscoutee-vm myscoutee-admin
openstack floating ip create public
openstack server add floating ip myscoutee-vm 198.51.100.42
    Replace the documentation addresses, server name, external-network name, and source CIDR with approved values. The floating-IP creation result supplies the real address used by the association command.
  5. From the management workstation, verify the host key obtained through the console and connect with ssh -i /path/to/key host-admin@198.51.100.42. When a bastion is required, configure OpenSSH ProxyJump or an equivalent approved route and place the corresponding option in the client configuration.
  6. Create the canonical A record in Designate when the cloud offers it, or in the organization’s external authoritative DNS. Verify the floating-IP and self-route behavior described in 5.6.
  7. Install the same released Debian package in the guest and use MyScoutee backup/restore procedures in addition to any Cinder snapshot or volume-backup policy.

OpenStack deployments vary: Horizon, Cinder, or Designate may be absent. Equivalent provider APIs, persistent block storage, and external DNS are acceptable when they satisfy the same host, persistence, network, and recovery contract.

5.6. Canonical Domain, DNS Records, and NAT Self-Access

Choose one canonical application FQDN, for example app.example.com. The value of DOMAIN is the DNS name only—without https://, a port, a path, or a wildcard. The matching browser origin, for example https://app.example.com, must appear in WEBSOCKET_ALLOWED_ORIGIN_PATTERNS.

Public DNS records for the canonical deployment
Record Use Guidance
NS Zone or subzone delegation Change registrar or parent-zone delegation only when Cloud DNS, Designate, or another provider becomes authoritative.
A app.example.com Canonical IPv4 endpoint Required for the direct-VM example; target the reserved address, public NAT/VIP, or floating IP.
AAAA app.example.com Canonical IPv6 endpoint Publish only after IPv6 routing, firewalling, Nginx reachability, and TLS have passed external tests. A broken AAAA record can make the application intermittently unreachable.
CAA Permitted certificate authorities Optional; if the zone uses CAA, authorize Let’s Encrypt or the operator-selected CA before issuance.
CNAME Alias or provider front-door hostname Not required for the canonical direct-VM deployment. Additional aliases and their certificates/redirects are not qualified by this single-domain package workflow.

Lower the DNS TTL before a planned cutover, then restore the organization’s normal TTL after the stable address is confirmed. Verify from an external resolver and from the VM:

dig +short A app.example.com
dig +short AAAA app.example.com
curl --fail --silent --show-error http://app.example.com/nginx-health

The Operator TLS domain test resolves the configured public name and requests its ACME challenge URL from the deployment host itself. A VMware or OpenStack VM behind NAT/VIP therefore needs working NAT reflection/hairpin routing, or a controlled split-DNS route that still reaches the same packaged Nginx endpoint. Test from an unrelated external network as well. Do not bypass a failed test by disabling certificate verification.

5.7. Firebase Project, Web App, and Server Credentials

Firebase is independent of the VM provider. Add Firebase to an approved Google Cloud project or create a dedicated production Firebase project, then register a Web app. Firebase Hosting is not required. Use the Web app configuration to collect the public client values: API key, default auth domain, project ID, storage bucket, messaging sender ID, app ID, optional measurement ID, and the public VAPID key.

  1. In Firebase Authentication, enable both Email/Password and Google sign-in. Configure the Google provider’s approved support identity.
  2. Add the canonical MyScoutee FQDN and the Web app configuration’s default <project-id>.firebaseapp.com auth domain to Authentication’s authorized domains. Keep the default Firebase auth domain in MyScoutee; a custom auth domain requires a separate Firebase Hosting/auth-handler design that this chapter does not implement.
  3. Enable Firebase Cloud Messaging and the APIs required for web registration and HTTP v1 sending. Generate or import a Web Push key pair and copy only its public VAPID key into the public-client field.
  4. Create dedicated service accounts in the same Firebase/Google Cloud project. A least-privilege starting point is Firebase Authentication Viewer (roles/firebaseauth.viewer) for the authentication credential and Firebase Cloud Messaging API Admin (roles/firebasecloudmessaging.admin) for the messaging credential. Confirm local policy and the built-in capability tests before granting anything broader.
  5. Create JSON keys only because the current MyScoutee interface requires complete service-account JSON documents. Treat each private key like a password: never commit it, bake it into an image, put it in browser configuration, or send it through email, chat, or a ticket.
  6. Sign in with the deployment-local bootstrap Operator and open Operator → Configuration. Enter the public values and paste the complete authentication and messaging JSON credentials into their separate fields. The two credentials and every public value must belong to the same project.
  7. Select Save Firebase, run Auth Test, allow browser notifications and run Message Test, then select Activate Firebase only after both tests pass. Verify sign-in, token refresh, notification permission, and a test notification in a fresh browser session.

The Browser API Key Is Not the Server Key

The Firebase API key and VAPID public key are public browser bootstrap values. The server credential is the complete service-account JSON containing a private key. MyScoutee encrypts Operator-managed credentials in MongoDB with the deployment master key and never returns their plaintext. Back up and restore that database and its matching master key as one unit.

For the current Operator-managed workflow, leave the startup compatibility flag FIREBASE_ENABLED=false. The package creates a non-secret {} placeholder for its declared Compose secret, starts with the deployment-local Operator credential, and uses the separately saved and activated encrypted credentials at runtime. Do not enable the legacy file-backed startup path for a new deployment. Perform key rotation by saving new JSON credentials, repeating both tests, activating the new revision, verifying a fresh session, and only then deleting the old Google Cloud keys.

5.8. Package Boundary, Operator Client Tools, and SSH Forwarding

A release build produces two deliverables with different execution locations. Neither changes the VM provider’s network or SSH policy.

Release installation and management artifacts
Artifact or path Execution location Purpose

The Debian package creates its directories and local secrets, loads the bundled application images, obtains missing pinned service images, and enables its systemd units. Direct apt installation deliberately leaves the application stack stopped for configuration. The client install.sh wrapper normally restarts and qualifies it because START_SERVICE=true is the client-bundle default.

The workstation bundle is GNU/Linux-oriented. It requires OpenSSH ssh/scp, APT package-inspection utilities (dpkg and dpkg-deb), OpenSSL, jq, tar, base64, od, sha256sum, GNU find/stat/ps, and the usual core utilities. Password transport additionally requires sshpass or setsid; key transport is preferred. Node.js 20 or later is recommended for the external smoke runner. The remote host must provide the supported Debian/Ubuntu APT environment, root or adequate sudo, and the separately prepared SSH service.

Authenticate and prepare the Operator client bundle

An authorized Operator with SFTP access can download the exact version-matched archive from an already installed host to the administrative workstation. Use the workstation's approved SSH configuration; do not place a password or private-key content in the command:

sftp myscoutee-host
sftp> get /usr/share/myscoutee/myscoutee-client-tools_1.0.0.tar.gz ./myscoutee-client-tools_1.0.0.tar.gz
sftp> bye

SFTP provides transport, not release authenticity. The archive must be authenticated before extraction, and every client helper—including install.sh, forward-localhost.sh, and verify-deployment—must be extracted and executed only on the trusted workstation, never on the deployment host.

Authenticate the client archive before extracting or executing anything from it. Use an already trusted copy of verify-release.sh—for example, one retained from a previously approved release, extracted from an independently authenticated package, or distributed through the organization’s controlled verifier channel:

/approved/trusted/verify-release.sh \
  myscoutee-client-tools_1.0.0.tar.gz \
  myscoutee-release_1.0.0.json \
  release-public-key.pem \
  sha256:<independently-obtained-64-lowercase-hex-characters>

mkdir myscoutee-client-tools-1.0.0
tar -xzf myscoutee-client-tools_1.0.0.tar.gz \
  -C myscoutee-client-tools-1.0.0
cd myscoutee-client-tools-1.0.0
cp install.env.example install.env
chmod 0600 install.env

Do not bootstrap trust by running the verifier from the same unauthenticated archive it is supposed to verify. The pinned fingerprint authenticates the release public key; it does not authenticate arbitrary verifier code obtained beside that key.

Set the SSH endpoint established in 5.3–5.5. A key-based production example is:

REMOTE_HOST=198.51.100.20
REMOTE_USER=host-admin
REMOTE_PORT=22
REMOTE_KEY_FILE=/absolute/path/to/id_ed25519
REMOTE_HOST_KEY_CHECKING=yes
START_SERVICE=true
STOP_ON_FAILURE=true
QUALIFY_TIMEOUT_SECONDS=300
RELEASE_MANIFEST_PATH=/approved/path/myscoutee-release_1.0.0.json
RELEASE_PUBLIC_KEY_PATH=/approved/path/release-public-key.pem
RELEASE_PUBLIC_KEY_FINGERPRINT=sha256:<64-lowercase-hex-characters>

The remote account must already exist, accept SSH/SCP, and be root or have the sudo authority required for APT, systemd, Docker, and package-owned host commands. If a bastion is required, use the workstation’s OpenSSH configuration or an approved quoted REMOTE_SSH_OPTIONS value such as "-J bastion-user@bastion.example.com". Prefer a dedicated SSH key. If REMOTE_PASSWORD or REMOTE_SUDO_PASSWORD is used, the helper rejects an install.env mode other than 0600 or 0400. The real install.env is deliberately absent from both release artifacts.

Pin the Host and Verify the Package

The example selects strict known-host checking. Populate the workstation’s known_hosts only after comparing the guest fingerprint through the provider console or another independent channel. Obtain the full release-key SPKI fingerprint through an independent release-authority channel as well; a public key downloaded beside the artifacts is not its own trust anchor.

Install, reinstall, or perform an approved manual upgrade

./install.sh /approved/path/myscoutee_1.0.0_amd64.deb

Before uploading anything, install.sh calls the packaged verify-release.sh. For a published release, the verifier requires all three configured release inputs and checks the independently pinned Ed25519 SPKI fingerprint, canonical signing-key ID and signatures for both release artifacts, declared size and SHA-256, canonical filenames, and the Debian package identity and version. It refuses an unverified package. ALLOW_UNSIGNED_LOCAL_PACKAGE=true is an explicit development-only escape hatch for an artifact built directly from a trusted local checkout; never use it for a downloaded or published artifact.

After verification, install.sh uploads the package to the configured simple path under /tmp, reads the installed version, calls remote apt-get install, and then invokes the package-provided qualify-deployment.sh. A same-version operation uses APT --reinstall without removing the package first. A downgrade is refused unless ALLOW_DOWNGRADE=true was explicitly approved. RUN_APT_UPDATE, START_SERVICE, STOP_ON_FAILURE, and the qualification timeout remain explicit local policy inputs. Setting START_SERVICE=false selects qualification of an already active service; it does not skip qualification or start a stopped service.

The wrapper does not run the public deployment smoke. SMOKE_PUBLIC_BASE_URL only makes it print the exact follow-up command; the external check must still run from the management workstation as described in 6.6.

Installable and Upgradeable Does Not Mean Self-Updating

A .deb file never upgrades itself. A newer package can be applied directly with apt or through the client wrapper, but both are manual administration paths. The installed product also contains the Operator-approved update path in Chapter 14: after explicit approval it verifies a newer signed .deb, requires a complete backup, invokes local apt-get install, restarts the service, and verifies the running images. It never polls and installs releases automatically, accepts only a version newer than the installed version, and performs no automatic data rollback.

Use the packaged SSH forward

After the same install.env target has been verified, the client bundle can create background, loopback-only forwards. Its defaults are:

sudo -E ./forward-localhost.sh
local 127.0.0.1:80  → remote 127.0.0.1:80
local 127.0.0.1:443 → remote 127.0.0.1:443

Local ports 80 and 443 require local privilege. To keep the local end unprivileged, override the mappings for one invocation:

LOCAL_FORWARD_PORTS_OVERRIDE=18080:80,18443:443 \
  ./forward-localhost.sh

Each comma-separated item is local[:remote]; one number means the same port at both ends. The script refuses a non-loopback local or remote bind, verifies that each forward starts, and replaces an exact existing SSH session for the same target and mapping. It uses background ssh -fN sessions and provides no stop command, so identify and terminate only the exact matching SSH process when diagnostics finish.

For a foreground one-off tunnel that ends with Ctrl+C, use OpenSSH directly:

ssh -N -o ExitOnForwardFailure=yes \
  -p 22 -i /absolute/path/to/id_ed25519 \
  -L 127.0.0.1:18080:127.0.0.1:80 \
  -L 127.0.0.1:18443:127.0.0.1:443 \
  host-admin@198.51.100.20

After installing a canonical-domain certificate, keep that domain as the TLS hostname and SNI while resolving only this high-port request to local loopback:

curl --resolve app.example.com:18443:127.0.0.1 \
  https://app.example.com:18443/api/health

https://localhost:18443 validates only when the selected certificate covers localhost, such as the package’s bootstrap certificate. For a private CA, supply its CA file to the client; do not disable certificate verification.

A tunnel does not install MyScoutee, create a public endpoint, change provider firewall rules, or prove public DNS, ACME, redirect, WebSocket, or Internet reachability. Do not use -k to hide a certificate failure. Complete the independent public checks in Chapters 6 and 13.

5.9. Worked Example: Mainland-China Country-Local Deployment

This example demonstrates the platform’s country-local capability in a demanding environment; the same pattern applies to other sovereign, disconnected, or policy-restricted networks. MyScoutee can run on an approved Debian/Ubuntu VM in a mainland regional cloud, local VMware/OpenStack environment, or authorized data centre. The application, persistent data, signed release artifacts, backups, monitoring, DNS, and—when required—a separately operated MyScoutee registry can remain on approved in-country network paths.

Country-Local Operating Outcome

Routine application operation does not require an always-available global registry. A deployment may remain registry-disabled, or it may select a qualified country-local registry so registration, signed feeds, and registry reporting stay regional. The standard signed Debian and client artifacts can be transferred through an approved offline or in-country release channel; GitHub, Docker Hub, and another foreign public service do not need to be deployment-time dependencies.

The objective is deployment locality and compliance, not circumvention of national controls. Qualify every required path from the real user and operator networks with the regional provider, security owner, and legal/compliance counsel.

Example deployment sequence

  1. Provision an amd64 Debian/Ubuntu VM on an authorized mainland provider or approved local infrastructure. Start with the Chapter 4 production baseline, assign a stable address, allow public TCP 80/443, and restrict SSH to the local administration network or bastion.
  2. Prepare the in-country domain, authoritative DNS, TLS route, ICP process, and any other required approvals before public launch.
  3. Transfer the approved signed release set into an in-country artifact service through a controlled import path. Pre-stage the Debian dependencies and all container images so installation, restart, certificate recovery, and rollback do not depend on GitHub, Docker Hub, or another cross-border source.
  4. Install and qualify MyScoutee through the same Debian/client-tools workflow used elsewhere. Keep monitoring, audit evidence, and encrypted backups on approved local services in separate failure domains.
  5. Choose the registry mode: operate locally with registry traffic disabled, or select a partnership-provided mainland MyScoutee registry endpoint and scope so registry reporting and signed feeds also remain regional.
  6. Test commissioning while cross-border access is deliberately unavailable. Enable only those external integrations—including Firebase—that are explicitly approved and proven reachable from both server and client networks.

6. Initial Installation and Commissioning

6.1. Verify the Package

For a published release, use the authenticated client workflow in 5.8 so the signed release manifest, Ed25519 signature, pinned key fingerprint, artifact size, SHA-256, and Debian identity are all verified before upload. The following inspection is useful additional evidence, but a bare digest without an independently authenticated value is not release authentication:

sha256sum myscoutee_1.0.0_amd64.deb
dpkg-deb --info myscoutee_1.0.0_amd64.deb

Compare the SHA-256 value with the approved release evidence. Do not install a package of unknown origin or with a mismatched digest.

6.2. Install

Use direct APT for an initial production installation when the host configuration must be reviewed before the first application start:

sudo apt install ./myscoutee_1.0.0_amd64.deb

Do Not Use dpkg -i by Itself

The package declares dependencies on Docker Engine and Docker Compose v2. The documented installation path is apt install ./…deb, which resolves dependencies before post-installation configuration.

Alternatively, the authenticated client-tools/install.sh path in 5.8 uploads through SSH, runs APT, and performs package-provided host qualification. Its default START_SERVICE=true immediately selects restart-and-check, so use that path for a fresh deployment only when starting with the packaged bootstrap configuration is approved. START_SERVICE=false means “qualify an already running service”; it is not a fresh-install pause switch.

During the initial installation, the post-installation process:

  1. creates the configuration, data, registry, update, TLS, log, and backup directories;
  2. creates the Operator configuration encryption key from 32 cryptographically random bytes represented as 64 lowercase hexadecimal characters;
  3. generates separate passwords for the MongoDB root user, the MongoDB application user, and MinIO;
  4. when OPERATOR_USER is empty, creates a deployment-local Operator identifier and a random 256-bit password;
  5. prints the password once, but stores only the identifier and the lowercase SHA-256 digest of the password;
  6. loads the five packaged MyScoutee images, verifies the image manifest, and pulls the configured MongoDB and Redis images if they are missing;
  7. enables myscoutee.service, the update and TLS path units, and the TLS renewal timer;
  8. does not automatically start the MyScoutee application stack.

Shown Once Does Not Mean Single Use

Immediately store the deployment-local Operator password displayed during installation in a secure secret store, and protect package-manager, terminal, and automation logs. The password remains valid for subsequent local Operator sign-ins until the deployment owner disables or replaces it; enabling Firebase alone does not invalidate it.

12. Restore and Disaster Recovery

Destructive Operation

The restore performs --drop against MongoDB and, when MinIO restore is enabled, deletes the current MinIO data directory. Before proceeding, exclude user traffic, preserve the pre-restore state, and verify that the correct backup has been selected.

12.1. Preconditions

  • The selected archive's SHA-256 digest and manifest have been verified.
  • The target is the same logical deployment or part of a documented clean-host disaster-recovery drill.
  • Compatibility between the installed package and the backup has been verified for the specific release.
  • The mongodb container is running.
  • User traffic is isolated.
  • A separate backup of the pre-restore state has been created, if still possible.
  • The required RESTORE_MINIO, RESTORE_CONFIG, and RESTORE_REGISTRY decisions have been approved.

12.3. Extended Restore

sudo env CONFIRM_RESTORE=true \
  RESTORE_MINIO=true \
  RESTORE_CONFIG=true \
  RESTORE_REGISTRY=true \
  /opt/myscoutee/packaging/scripts/restore-production.sh \
  /var/backups/myscoutee/myscoutee-backup-YYYYMMDD-HHMMSS.tar.gz
Switch Effect Risk
RESTORE_CONFIG=true Copies the saved .env, .env.secrets, and Compose file back into the server tree. In an installed environment, verify the relationship between /etc/myscoutee and the server symbolic links after restore.
RESTORE_MINIO=true Stops MinIO, deletes the current data directory, extracts the backup, and restarts MinIO. The current object state is lost.
RESTORE_REGISTRY=true Validates and restores the complete deployment key pair, state, and receipt history. Transfers signing control of the registered deployment; never clone it to an independent installation.

Registry restore rejects a key-only backup, a mismatched Ed25519 key pair, an invalid fingerprint/state binding, and invalid receipt cryptography.

Clean-Host Disaster Recovery Is Not Generally Proven

The restore script includes strong technical checks, but the repository qualification document requires a separate clean-host restore and an upgrade drill from the oldest supported version for every release. Source tests or the successful extraction of one archive alone do not prove RTO, RPO, or complete recoverability.

Incomplete Cryptographic Restore

If replacement of the MongoDB/key pair or registry identity/state is interrupted, the script may intentionally leave the Java API stopped. Do not restart the API blindly; first establish the cause and verify the key/data pair in use.

13. TLS and Certificate Lifecycle

Production Nginx always expects TLS. It redirects normal HTTP application requests to HTTPS with status 308, except for /nginx-health and the ACME challenge path. HTTPS responses include a one-year HSTS header.

13.1. TLS Modes

Mode Switch Container path Host storage
Operator-managed LETSENCRYPT_ENABLED=false /etc/nginx/keys/nginx.crt and nginx-nopass.key, or a configured absolute path /opt/myscoutee/server/docker/conf/nginx/keys
Let’s Encrypt LETSENCRYPT_ENABLED=true /etc/letsencrypt/live/<DOMAIN>/fullchain.pem and privkey.pem /var/lib/myscoutee/data/certbot/conf

When both operator-managed TLS files are absent, package configuration creates a matching self-signed RSA-2048/SHA-256 bootstrap pair valid for 3650 days, with common name localhost and subject alternative names DNS:localhost and IP:127.0.0.1. The certificate is mode 0644 and its private key is mode 0600. This pair is for local inspection only and is not a trusted public certificate for the deployment FQDN. An existing complete pair is preserved byte-for-byte; if exactly one file exists, it is preserved and configuration fails closed, as described in the TLS backup-gap callout below.

13.2. Recommended Operator Workflow

  1. Point public DNS to the deployment and make TCP ports 80 and 443 reachable.
  2. Sign in to Configuration as an authenticated Operator.
  3. Enable HTTPS management and choose automatic or manual mode.
  4. Enter the public domain and, in automatic mode, the certificate contact email address.
  5. Run the domain and certificate test.
  6. Save the block; changing the toggle alone creates only a draft.
  7. In automatic mode, enable and save automatic renewal.
  8. Verify that Nginx restarts and that the external trust chain is valid.

The privileged TLS worker accepts only a fixed-schema JSON request; it does not accept arbitrary commands, paths, images, or URLs from the browser. For a manual key pair, it verifies that the certificate and key match, that the certificate covers the domain, and that the certificate remains valid for at least 24 hours.

TLS Backup Gap

The production backup script saves neither the manual Nginx key pair nor the Let’s Encrypt directory. These require a separate encrypted backup and reissuance procedure. Normal remove, deconfigure, upgrade, and same-version reinstall preserve a complete manual Nginx certificate/key pair. Package configuration creates the bootstrap pair only when both files are absent; if exactly one exists, it preserves that file and fails closed so the Operator can restore its counterpart. An explicit apt purge deletes the pair with /opt/myscoutee.

Enabling and Provisioning Are Separate Operations

LETSENCRYPT_ENABLED=true does not request a certificate; it only activates an existing certificate/key pair located exactly under DOMAIN. Nginx startup fails when the pair is missing or invalid.

14. Operator-Approved Updates

A registry UPDATE announcement only reports an available release. Download and installation occur solely after explicit approval by an authenticated Operator. The Debian package installs this local update mechanism; no remote shell session or separate remote automation is required, and neither the package nor the worker performs unattended polling and installation.

14.1. Prepare the Host

  1. Through an independent channel, verify the full SPKI DER SHA-256 fingerprint of the vendor's Ed25519 release public key.
  2. Install the key: 
    sudo install -m 0640 -- release-public-key.pem \
  /etc/myscoutee/update/release-public-key.pem
sudo chown +0:+10001 -- \
  /etc/myscoutee/update/release-public-key.pem
sudo chmod 0640 -- \
  /etc/myscoutee/update/release-public-key.pem
  3. Verify the local fingerprint: 
    sudo openssl pkey -pubin \
  -in /etc/myscoutee/update/release-public-key.pem \
  -outform DER | sha256sum
  4. Configure the gate: 
    sudoedit /etc/myscoutee/myscoutee.env
# MYSCOUTEE_UPDATE_ENABLED=true
sudo systemctl restart myscoutee
sudo systemctl restart myscoutee-update.path
  5. Verify the path unit: 
    sudo systemctl status myscoutee-update.path --no-pager

14.2. Operator Approval

Before selecting Update deployment, open Operator → Community, locate the current published UPDATE announcement, and expand Details. Proceed only when:

  • the announcement is Published, not archived or withdrawn;
  • the displayed target version is the approved release and the separately approved release evidence confirms its release channel;
  • the artifact size and compatibility range are acceptable for the installed version and maintenance window;
  • SHA-256 is present in canonical sha256:<64-lowercase-hex-characters> form;
  • Package signing key ID is the expected pkey_<32-lowercase-hex-characters> value derived from the independently pinned release key;
  • Canonical Ed25519 signature is present, and Signature verification explicitly reads Release metadata verified by the pinned key; never proceed when it reads Release metadata not verified by the pinned key;
  • the artifact address is the expected credential-free HTTPS .deb URL and is labelled Verified release URL;
  • free space for staging and cache and the ability to create a complete pre-update backup have been confirmed.

    • Then open Operator → Updates and confirm that Available version exactly matches the version reviewed in Community. Selecting Update deployment is the approval action and begins the update immediately; the current Updates popup does not repeat the cryptographic fields or add another confirmation dialog.

    What the Pre-Approval Verification Proves

    The shortened package-signing key ID does not replace the independently verified full SPKI fingerprint in 14.1. The positive UI status authenticates the signed version, channel, size, and digest metadata with the locally pinned key; signature presence alone is not proof. The package bytes have not yet been downloaded at this point. Their final size and SHA-256 are checked during the subsequent verification phase and again by the privileged host worker.

    14.3. Execution Chain

    1. The Java API starts from the credential-free, fragment-free HTTPS .deb URL in the registry-signed manifest. It may follow at most five loop-free HTTPS redirects that remain credential- and fragment-free, accepts only a final HTTP 200 response, enforces the signed and configured size limits while streaming, and verifies final size and SHA-256.
    2. The API writes to staging, then publishes a fixed-schema request to the host inbox.
    3. The systemd path unit starts a root worker, which atomically claims or quarantines the input.
    4. The worker independently revalidates the package name, version, architecture, size, digest, release key ID, Ed25519 signature, image manifest, and free space.
    5. It creates a mandatory production backup with complete: true.
    6. It runs apt-get install from a local file.
    7. It restarts the stack and, for up to 300 seconds, verifies the exact reference, ID, and health of each of the four managed running images.

    Default storage limits:

    • Java staging safety reserve: 512 MiB in addition to the artifact size;
    • root cache minimum free reserve: 512 MiB in addition to the artifact size;
    • root cache retention: two jobs;
    • maximum artifact size: 4 GiB.

    14.4. Monitor Progress

    sudo journalctl -fu myscoutee-update.service
sudo cat /var/lib/myscoutee/update/runtime/jobs/<job-id>/status.json
sudo tail -f /var/lib/myscoutee/update/runtime/jobs/<job-id>/install.log

    Terminal states are COMPLETED, FAILED, REJECTED, and RECOVERY_REQUIRED.

    No Automatic Data Rollback

    If installation is partial or cannot be verified, the worker sets RECOVERY_REQUIRED. It does not automatically restore the previous data or package. Use the backup recorded in the status, the installation log, and the release-specific recovery procedure.

    14.5. Recovery

    sudo journalctl -u myscoutee-update.service
sudo cat /var/lib/myscoutee/update/runtime/jobs/<job-id>/status.json
sudo cat /var/lib/myscoutee/update/runtime/jobs/<job-id>/install.log
sudo env CONFIRM_RESTORE=true \
  /opt/myscoutee/packaging/scripts/restore-production.sh \
  /var/backups/myscoutee/<backup-recorded-in-status>.tar.gz

    Uninitialized Registry and the Update Gate

    The backup helper treats the registry key and state as part of completeness. Before registry initialization, a backup with MYSCOUTEE_BACKUP_REQUIRE_COMPLETE=true fails, so the privileged update worker does not reach installation. Do not bypass this by manually creating files.

    During a failed Debian package transaction, postinst abort-upgrade, abort-remove, and abort-deconfigure return without rerunning the full configuration path. This protects existing keys, bootstrap material, TLS files, and configuration from recovery side effects; it is not an automatic rollback or repair. Inspect the APT, dpkg, and service logs, recover the package transaction through the approved package-manager procedure, and then rerun the explicit deployment qualification before restoring traffic.

    Manual apt install ./new-package.deb is technically possible, but it bypasses the Operator update rail's manifest, signature, complete-backup, and progress controls. Use it for a production update only as an approved, release-specific documented exception.

15.2. Registration Flow in the Current Registry Dialog

  1. The system operator sets the host-level REGISTRY_OUTBOUND_ALLOWED kill switch to true only after outbound registry traffic has been approved.
  2. The authenticated Operator opens the Registry dialog. The current field is a read-only catalog selector: the Operator selects one of the offered HTTPS endpoints and its cataloged scope.
  3. The Operator initiates Register. The frontend sends the selected registryBaseUrl and expectedRegistryScope values to /api/operator/registry/register.
  4. As part of the same registration action, the Java backend performs a live registry identity inspection, verifies the expected scope and any compatible existing binding, and persists the selection.
  5. The backend locally creates or loads the Ed25519 deployment identity and performs registration synchronization.
  6. The backend verifies the registry-signed receipt against the pinned registry public key and stores it persistently.
  7. The dialog displays the lifecycle state, current URL, and success or failure of the action. Use Disconnect to terminate an active connection.

TOFU and Plain HTTP

Trust on first use and insecure HTTP are disabled by default in production. Do not enable them for a real registry merely for convenience. An insecure HTTP exception is only for controlled development hosts with an explicit allowlist; wildcards are not supported.

Control Gap: the Planned Two-Phase Confirmation Is Not Connected to the Current Dialog

The project context specifies a separate read-only inspection, display of the registry signing identity and fingerprint, and then explicit Operator confirmation. The backend /inspect and /confirm APIs and corresponding frontend store methods exist, but the current Registry dialog does not call them: Register invokes the single-phase /register action directly and does not display a separate fingerprint confirmation. Therefore, the current dialog must not be documented as satisfying the planned two-phase human identity control. Before enrollment with a real production registry, the release manager must treat this as an open control gap, independently approve the catalog endpoint and scope, and document either the accepted residual risk or the corrected release.

15.3. Persistent Identity and State

/etc/myscoutee/registry/deployment-private-key.pem
/etc/myscoutee/registry/deployment-public-key.der
/var/lib/myscoutee/registry/deployment-state.json
/var/lib/myscoutee/registry/receipts/

The private key is PKCS#8 PEM with mode 0600; the public key is X.509 SPKI DER. The backend runs as unprivileged UID/GID 10001 but receives writable access to the registry key directory because the explicit Operator action publishes the first key pair there.

Boundary of Backend Compromise

The Java backend is the registry's only network client and possesses the deployment private key. Compromise of the backend process also endangers this key; never share the directory with another service.

15.4. Changing Registries

Changing to another registry is not a simple URL edit. The current registry must first receive a signed unregister/deactivation; only then may the old binding and receipts be archived while retaining the node key. History, claims, ledger entries, and registry identity are not migrated automatically.

15.5. Registry Operations Checklist

  • The state of the host outbound kill switch is documented.
  • The registry URL and scope selected from the read-only catalog have prior release- or deployment-level approval.
  • The risk decision for the gap between the current single-phase dialog and the planned two-phase fingerprint confirmation is documented.
  • The registry receipt verified by the backend and the deployment state are preserved in backups.
  • The deployment key and its associated state/receipts are included together in the backup.
  • After restore or a registry change, outbound access was enabled only with verified state.
  • The internal Explore registry is not confused with the real registry.

16. Security Operations

Host and Network

  • Expose only ports 80 and 443 publicly; the MongoDB host mapping must remain on loopback.
  • MinIO, Redis, the Java API, and the Explore registry publish no host ports.
  • Treat access to the Docker socket and membership in the docker group as equivalent to root privileges.
  • Use a separate host-patching process for operating-system and Docker security updates; the MyScoutee package does not perform aggressive system upgrades.
  • Verify that administrative access will be preserved before changing firewall rules.

Application and Container Boundaries

  • The Java production image runs as UID/GID 10001 and exits when an out-of-memory condition occurs.
  • The Explore registry uses a read-only root filesystem, no-new-privileges, and drops all capabilities.
  • The TLS and update workers run as root but use fixed host paths and narrowly defined input schemas.
  • For managed application images, pull_policy: never prevents silent image replacement behind a tag.
  • The Nginx and backend upload limit is 10 MB.
  • The backend does not expose detailed production health information; metrics require administrator privileges.

Secret and Key Management Rules

  • Never place a private key or service account in Git, an image, a ticket, or chat.
  • The release private key must never exist on an application deployment or registry server.
  • Backups are encrypted, access-logged, and stored off-host.
  • The deployment master key cannot be rotated without atomically re-encrypting every encrypted record.
  • The registry deployment key may be restored only with a complete state/receipt recovery set.
  • The shown-once Operator credential and installation log are protected.
  • External provider credentials are handled through the authenticated deployment-configuration process; the package contains only empty templates.

Separate Public and Secret Data

Endpoints, fingerprints, public verification keys, Firebase web-client identifiers, and the VAPID public key are not server-authentication secrets. The Firebase service-account private key, payment/email/social tokens, MongoDB and MinIO passwords, deployment private key, and master key are secrets.

19. Removal and Reinstallation

Remove the Package While Retaining Data

sudo apt remove myscoutee

The process stops and removes the Compose containers and disables the application, update, and TLS units. It retains substantial state under /etc/myscoutee and /var/lib/myscoutee, the complete manual TLS pair under the otherwise removed package tree, the demo registry volumes, and MyScoutee image tags for a later reinstallation. The package-owned archive at /usr/share/myscoutee/myscoutee-client-tools_1.0.0.tar.gz is removed; a separately downloaded and extracted workstation copy is unaffected.

Manual TLS Pair Is Preserved Until Purge

Normal remove, deconfigure, upgrade, and reinstall preserve a complete nginx.crt/nginx-nopass.key pair. This lifecycle preservation is not a backup: keep a separate protected copy or reissuance procedure. A partial pair makes package configuration fail closed, and purge removes the entire /opt/myscoutee tree.

Complete Purge

sudo apt purge myscoutee

The trusted workstation bundle also provides ./purge.sh, which invokes remote apt-get purge -y myscoutee and deletes the uploaded .deb. It has no interactive confirmation or dry-run mode. Use it only after completing the checklist below; it is not part of a normal reinstall or upgrade.

Purge Causes Irreversible Data Loss

Purge deletes the /etc/myscoutee, /opt/myscoutee, /var/lib/myscoutee, /var/log/myscoutee, and update-cache trees; both Explore registry volumes; and every myscoutee-api, myscoutee-nginx, myscoutee-minio, and myscoutee-registry image tag. It does not delete shared upstream MongoDB/Redis images or /var/backups/myscoutee. A complete off-host backup and registry identity/state verification are mandatory before purge.

Pre-Removal Checklist

  • Final removal has been approved.
  • A complete backup, its SHA-256 digest, and an off-host copy are available.
  • The separate backup gaps for TLS, Firebase, and the update key have been addressed.
  • The need for a registry deactivation/exit procedure has been assessed.
  • The legal basis for retaining the deployment private key and receipt history is documented.
  • After purge, the backup remains reachable and readable.

20. Known Operational Limitations

Sizing No qualified universal throughput, user-count, or capacity limit, and no container resource limits. Use the Chapter 4 planning baseline, then perform release- and deployment-specific load/capacity testing and host monitoring.

The limitations listed here do not authorize bypassing controls. The appropriate response is a documented compensating control, a qualification drill, or a new software release.

Appendix A — Source Build, Package Build, and Development Profile

This appendix covers the repository's complete lifecycle. The build and development profiles described here are not the same as the apt-installed production profile operated in the main body of this manual.

A.1. Build Production Artifacts from Source

From the repository root:

MYSCOUTEE_VERSION=1.0.0 \
  bash packaging/scripts/build-production.sh

By default, the script builds and synchronizes the production frontend bundle, runs the Gradle bootJar build, creates the base Nginx image, and then builds the source-production Compose images. The build environment must also have access to the adjacent MyScoutee registry source.

A.2. Build the Debian Package and Client Bundle

In one step, including an automatic artifact build:

MYSCOUTEE_VERSION=1.0.0 \
  bash packaging/scripts/package-production.sh

If the preceding production build was created from exactly the same source state and version, avoid rebuilding it:

MYSCOUTEE_VERSION=1.0.0 \
  BUILD_ARTIFACTS=false \
  bash packaging/scripts/package-production.sh

Expected outputs are packaging/dist/myscoutee_1.0.0_amd64.deb and packaging/dist/myscoutee-client-tools_1.0.0.tar.gz. The package build saves the five managed MyScoutee images into the Debian archive, creates an image manifest, runs a credential audit, embeds a byte-identical copy of the versioned client archive at /usr/share/myscoutee/myscoutee-client-tools_1.0.0.tar.gz, and emits the standalone workstation archive. It does not install expanded client scripts on the deployment host. The source-only convenience entry point tools/build-debian-release.sh invokes the same package builder.

Building does not by itself establish a published release. On an isolated release workstation, use the source-only tools/sign-release-artifacts.sh with an approved pre-existing Ed25519 PKCS#8 private key to validate and sign the matching Debian and client artifacts and to produce myscoutee-release_1.0.0.json. The signing tool neither creates nor copies the private key. Publish the Debian package, client archive, signed manifest, and public key; distribute the full SPKI fingerprint through an independent trusted channel. Production use still requires release qualification and approval.

The release lifecycle is therefore: build both artifacts; sign them on the controlled release host; publish the two artifacts, signed manifest, and public key; authenticate the full SPKI fingerprint independently; verify the client archive with an already trusted verifier; extract it; and let its installer reverify the Debian package before SCP and APT.

A.3. Development Stack

cd server
docker compose up --build

The development stack uses hot reload, workspace mounts, development/demo helpers, and services that can be inspected on loopback. The sibling myscoutee-registry repository is required to build the real Go registry sandbox.

The Profiles Are Not Interchangeable

The development stack, source server/docker-compose-prod.yml, and packaged /opt/myscoutee/server/docker-compose-prod.yml use different build policies, host paths, health timing, and security/operations boundaries. Development docker compose up --build does not replace Debian package installation, the systemd lifecycle, production TLS, guarded backup/restore, or the signed update rail.
