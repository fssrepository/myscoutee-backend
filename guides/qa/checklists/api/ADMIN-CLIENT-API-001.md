Status: **IN PROGRESS — user-started dev stack, 2026-09-23.**
New API-domain case, version **1.0.2**. Codex is explicitly authorized to perform this entire flow automatically; user observations during the run are corrections, not a pause. Existing PASS cases stay unchanged.

## Baseline

1. Verify the already-running dev stack and existing watcher logs. Record backend/frontend/client commits. Use the versioned admin-client fixture and managed browser launcher below. Do not start a second stack or compiler.
2. Run `python3 guides/qa/tools/admin-client-api-fixture.py stage`, then `status`; launch `node guides/qa/tools/open-checkpoint-browser-sessions.mjs ADMIN-CLIENT-API-001`. The fixture creates two active profiles and inactive/blocked/deleted controls; capture the existing statistics snapshot before the ordinary telemetry worker refreshes. Use Ava and the disposable normal user's windows.
3. Install the locally built `myscoutee-client-admin/dist/myscoutee-client-admin_1.0.2_all.deb` into a disposable package root or isolated test system. System-wide installation is not required for automated QA on the user's workstation. Verify desktop entry, executable and package metadata. Start the extracted executable through the source-equivalent launcher; do not use real production keys.

## Numbered flow

4. Ava profile: button says **API**, common popup shows private base URL and key management, no personal referral link, invited/imported badges or batch-size hint. GitHub link targets the private `myscoutee-client-admin` repo. Normal user's popup still says Affiliate and retains referral behavior.
5. Create one admin API key through confirmation. Copy it into the client in memory; never write the key into evidence/logs/screenshots. Settings reload exposes only its prefix/claim metadata. A normal user cannot read/create/revoke admin keys; an admin cannot revoke someone else's key.
6. Connect with the popup's URL, demo-data mode and a ten-second interval. Inspect `/admin-client/v1/overview`: only aggregate statistics and attention fields, no message bodies, user list or moderation actions. HTTP mode is allowed only on loopback; remote URL requires HTTPS. User can replace the URL after Disconnect. Live/demo datasets must not mix.
7. Compare active-profile gender counts with the statistics snapshot produced by the existing worker. The two active fixture actors contribute +1 female/+1 male; inactive, blocked, deleted and staff do not contribute. Compare 7/30 registration totals with `adminStats.dailyActivity[*].registrations`, last 7/30 UTC dates including today. Opening/using a profile must not count as registering. Missing/stale snapshot is shown with readiness/time, not silently called live.
8. Change polling to 5 seconds and 20 seconds while connected. Observe request timing and that only one request is in flight. Introduce a slow/unreachable URL using the local stub: timeout leaves last data visibly stale and retries without overlapping requests. Invalid intervals are rejected.
9. Normal user sends an App Support message / submits a report through the app. Verify unread/open attention changes after ordinary backend persistence. Client emits one desktop notification when supported, without message text. Repeat the same successful poll: no repeat notification. A second new unread message must notify even if the unread total coincidentally stays the same. Counts decreasing do not notify. Automatic content moderation alone is not a notification source.
10. Close the client window and send another message. Verify the same background process continues polling and invokes the notification mechanism. Reopen via the launcher: same local port/process/connection and retained data, with no new Connect required. A second launcher must not create a second watcher. The UI's one-second local-state refresh must not become one-second remote polling. Verify the Ubuntu notification center application name/icon, and normal Do Not Disturb behavior. The installed XDG desktop-login entry starts the same singleton without opening a window; disconnected startup emits no poll or notification. Do not log out the user's desktop for this check: inspect the installed entry and invoke that command in the isolated test environment. A real logout/reboot clears the RAM-only key and requires Connect again.
11. Open MyScoutee from the monitor: ordinary application login remains required. The key itself does not log the browser in or authorize handling a report. Client supports no accept/reject/block mutation.
12. Disconnect during a pending poll: key is cleared, polling stops, a late response cannot restore data or notifications. Reconnect with the same stable client identity; a different client UUID using an already-claimed key is rejected. Stop/restart the background process: URL/interval persist, secret does not; a new Connect is necessary.
13. Negative API checks: missing/expired/revoked key, affiliate key against private API, admin key against public affiliate API, removed/inactive/blocked admin, guessed key ID for revocation. Expect 401/403 (or 404 for an unowned key); no private response. Revoke the connected key in Ava's popup: next poll clears connection with an explicit authorization error.
14. Verify EN/HU UI, key absent from browser state responses/preferences/logs, no authorization forwarding on HTTP redirects, loopback binding, local control-token/origin protections, clipboard/copy/confirmation behavior and background shutdown cleanup. Record exact versions and elapsed time, not secrets.
15. Preserve evidence per numbered step, close only checkpoint windows, stop only this test client's background process and reset `admin-client-api-fixture.py reset`. Remove test tokens via the normal UI. Shared admin support audit messages remain as evidence; do not reset unrelated users or admin counters.
