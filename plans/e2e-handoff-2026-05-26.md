## Server `subevent-resources` Test Issue

Last server e2e run before this handoff:

- Result: `60 passed, 1 failed, 7 skipped, 68 selected`
- Failure: `event-editor/subevent-resources`
- Error: response body was `null`, while the test expected an object.

Important interpretation:

- `null` is not automatically an app bug.
- The endpoint `/api/activities/events/subevent-resources` returns `null` when no resource state exists for the exact `(ownerId, subEventId, assetOwnerUserId)` combination.
- The old generic `subEvent` requirement only guarantees an event with at least one sub-event. It does not guarantee that the selected user owns/has resource state for that sub-event.
- This is different from "there are no sub-events". The event/sub-event can exist and the resource state can still be absent for that asset owner.

Do not blindly hide this with dynamic discovery unless the test contract is agreed.

Recommended choices:

1. Fixed fixture contract:
   - Put known demo fixture IDs into the request for an event/sub-event/asset-owner combination that has resource state.
   - This is the most Postman-like and easiest to debug.
2. Nullable contract plus separate positive fixture:
   - Allow `null` for the generic read case.
   - Add a second explicit fixture-backed case that asserts the full object shape.
3. Playground setup:
   - In playground mode, create/replace sub-event resource state first, then query it.
   - Best for destructive lifecycle coverage, but not a static contract smoke.

Avoid adding `prepare.mjs` again without explaining which of the above contracts is being implemented.
