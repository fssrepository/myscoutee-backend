MongoDB features:
-----------------

Change Streams
A MongoDB feature where the app listens to DB changes in real time.
Example: “when a chat message document is inserted, push it to websocket”.

Vector Search
Used for semantic / AI-style search.
Example: store embeddings for users/events/assets, then ask “find similar profiles/events”.

Time Series
MongoDB collection type optimized for timestamped measurements.
Example: CPU metrics, event telemetry, sensor data, request latency logs.

Atlas Search
MongoDB’s advanced full-text search product, mainly tied to MongoDB Atlas.
Example: fuzzy search, autocomplete, relevance scoring.

Spring Security already has the building blocks.
------------------------------------------------

In this repo we already have `spring-boot-starter-security` and a `SecurityFilterChain` in [WebSecurityConfig.java](/home/raxim/workspace/myscoutee-backend/server/projects/profile/src/main/java/com/raxim/myscoutee/common/config/WebSecurityConfig.java:48). That currently protects mostly by URL/admin/authenticated rules.

For the thing you mean, Spring has:

1. **Method security**
   Enable with `@EnableMethodSecurity`, then use `@PreAuthorize` on controllers or services. Spring docs say Boot starter security does not enable method security by default, and enabling it lets you authorize method calls using inputs/return values. Source: Spring Security method security docs.  
   Example:
   ```java
   @PreAuthorize("@accessControl.can(authentication, 'asset.edit', #request.assetId())")
   public AssetCardDto updateAsset(AssetUpdateRequestDto request) { ... }
   ```

2. **Custom authorization service**
   This is probably best for us:
   ```java
   @Component("accessControl")
   class AccessControlService {
       boolean can(Authentication auth, String permission, String objectId) {
           // lookup ActivityMember / grants / owner relationship / etc.
       }
   }
   ```
   Then every endpoint/service can ask the same place.

3. **PermissionEvaluator / `hasPermission(...)`**
   Spring Security has a `hasPermission` hook for object-level authorization through a `PermissionEvaluator`. Source: Spring docs mention `hasPermission` as the object-level hook.

4. **AuthorizationManager**
   Newer Spring Security authorization is centered on `AuthorizationManager`, used for request-level and method-level decisions. Source: Spring authorization architecture docs.

5. **Spring Security ACL**
   There is an official ACL module, but I would be careful. It is JDBC/table based, expects ACL schema, and many parts assume long-compatible object IDs. The docs explicitly mention ACL tables and long ID expectations. Since this project is Mongo/string-ID/domain-rich, I would likely **not** start with Spring ACL. I’d build a small app-specific policy layer using Spring method security.

So the practical path here would be:

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class WebSecurityConfig {
}
```

Then centralize checks into something like `AccessControlService` / `PolicyService`, and gradually replace scattered owner/member/manager checks with:

```java
@PreAuthorize("@accessControl.can(authentication, 'resource.assign', #request.ownerId())")
```

One important thing: we should not trust `userId` from request bodies for authorization. Actor should come from `SecurityContext` / Firebase auth, then request `userId` can be validated against that where needed.

Yes, I agree with the direction. What you are describing is the right class of fix: central authorization instead of scattered `if user is owner/manager/member` checks inside many service methods.

One nuance: `userId + somethingId + edit/delete` is more an **ACL** model than pure RBAC. For this app I’d use a hybrid:

- **RBAC**: roles like `Admin`, `Manager`, `Member`, scoped to `event`, `asset`, maybe `subEvent`.
- **Permissions**: actions like `event.edit`, `event.delete`, `asset.manage`, `asset.borrow.approve`, `resource.assign`, `member.remove`.
- **Relationship rules**: derived checks like “accepted member of this event” or “manager of this asset”.
- **Optional ACL/grants**: explicit overrides only where needed.

So instead of hardcoding:

```java
if (!isOwner && !isManager) return null;
```

we move toward:

```java
authorization.require(userId, "resource.assign", ResourceRef.event(eventId), context);
```

or controller/AOP style:

```java
@RequiresPermission(action = "resource.assign", resourceType = "event", resourceId = "#request.ownerId")
```

But I would still keep **business invariants inside services**. Example: “to assign or borrow a car for an event, the user must already be an accepted event member” is not just UI/controller authorization; it is a domain rule. AOP can block API misuse, but service logic should still enforce invariants because services may be called from tests, schedulers, admin flows, or future endpoints.

The clean architecture I’d aim for:

1. `AuthorizationService`
   - central `can(...)`, `require(...)`
   - deny by default
   - logs/audits denials

2. `Policy` classes
   - `EventPolicy`
   - `AssetPolicy`
   - `ResourceAssignmentPolicy`
   - these encode rules in one place instead of random services

3. Existing `ActivityMember`
   - remains the scoped role source:
   - `ownerType=event`, `ownerId=eventId`, role `Member`
   - `ownerType=asset`, `ownerId=assetId`, role `Manager`

4. Optional new collection later
   - maybe `access_grants`
   - fields: `subjectUserId`, `resourceType`, `resourceId`, `permission`, `effect`, `expiresAt`, `createdBy`
   - used for explicit exceptions, not every normal role

For the current manager/resource work, your instinct is exactly right: don’t spread “manager means X” everywhere. This change should probably become the first small step: keep the event/asset roles separate, and next introduce one central authorization/policy layer so edit/delete/assign/borrow checks stop being custom one-offs.
